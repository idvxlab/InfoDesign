# B2 provider_failed 无网络诊断与修复

本轮没有再次请求真实网关，也没有改动凭据。已发现并修复模型兼容配置丢失的问题。该问题可在本地模拟中复现首次调用即失败的现象，但首次真实任务的 HTTP 状态和原始错误未保留，不能认定这是那次失败的唯一原因。

## 可确认的证据

- 实际配置选择 `company-gateway` / `deepseek-v4.1-flash`，API 为 `openai-completions`，base URL 以 `/v1` 结尾。SDK 构造 `/v1/chat/completions`，没有重复 `/v1` 或错用 Responses API。
- 既有提供方配置明确含 `compat.maxTokensField: max_tokens`；模型条目没有覆盖这一项。只读取兼容字段和公开端点元数据，没有输出 API key。
- 旧 `readModelConfig`、CLI 及 `session-factory` 只保留提供方、模型、端点和 key，没有把兼容项交给 SDK。
- 锁定 Pi SDK 0.99.1 根据提供方／域名识别协议默认值。该自定义网关不会被识别为 DeepSeek 官方地址，缺少显式兼容项时使用 `max_completion_tokens`。
- 在 `--network none`、无真实凭据的独立容器中，拦截 HTTP 传输并返回合成响应。旧映射实际构造 `max_completion_tokens: 1024`；按既有配置要求 `max_tokens` 的本地模拟端点返回 400，结果为 1 次模型尝试、0 次工具读取。显式传入兼容项后请求变为 `max_tokens: 1024`，模拟流程完成 2 次模型响应和 1 次读取。

上述 400 是本地合成响应，并非恢复或猜测出的真实网关响应。首次真实验收报告只有 `provider_failed`、程序耗时 54 ms 和缺失用量；标准错误为空，代理 `access_log none`。当前无法从它确定请求是否到达网关，也无法排除当时的连接、认证或其他请求兼容问题。不能把 54 ms 或无用量解释为免费。

## 最小修复及诊断

1. `ModelConfig` 增加可选的 `maxTokensField`，只允许 `max_tokens` 或 `max_completion_tokens`。
2. `readModelConfigFromModels` 读取明确选择的模型和提供方配置，保留该兼容项；模型级覆盖提供方级。CLI 复用这个入口，模型文件中的 `apiKey`、headers 或命令字符串不会被执行或转为凭据。
3. 会话工厂将该字段传入 SDK 模型定义的 `compat`，不针对所有网关强行使用同一默认值。
4. `transport-diagnostics.ts` 包装现有 fetch，保留原来的请求、代理、响应和异常行为；只记录尝试次数、HTTP 状态及固定白名单错误码。它不读取错误响应正文，不保存 URL、请求头、原始异常或 API key。未知错误码记为 `unknown`。

有了这些诊断，后续能够区分“尚未进入 fetch”“进入 fetch 但发生连接错误”“得到 HTTP 错误状态”等阶段，但 fetch 计数仍不证明远端已接收或计费。旧验收报告保持原样，不能补造当时不存在的诊断字段。

一次性用户资料验收脚本也必须复用 `readModelConfigFromModels`，不能继续手写只取 base URL 的旧映射。前次私有脚本作为历史证据保留，不能直接重跑或覆盖其执行标记。
