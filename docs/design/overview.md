## 需求与范围

本节概括已确认的讨论及用户提供的《智能信息设计系统项目需求说明书》，不包含需求书全文。
后续以原始需求和用户明确确认的修改为准；本骨架没有复制原始 PDF、PPT 或 DOCX。

### 面向企业的目标

系统从多模态资料中识别企业、品牌、业务、产品、技术、资质、发展历程、应用领域及其关系，再根据用户目标自主组织信息、选择表达方式，形成可交互、可追溯的展示成果。范围不限于企业产品目录，也不按固定整页模板填空。

### 必需能力

- 多模态信息理解、实体、事实、关系和事件提取及跨文件归并。
- 关键事实保留文件版本与具体位置，识别冲突，不将推测作为确定事实。
- 先决定内容选择、分组与浏览路径，再细化视觉、布局和交互。
- 支持用户自然语言修改，保留已确认信息与设计约束，避免重做无关内容。
- 自动验证事实、完整性、数据、来源、视觉与交互，发现问题后定向修正。
- 无法判断时提示问题；正常输出不依赖每步人工批准。

### 需求出处

需求书第 1—2 页：定位、企业信息与关系；第 3 页：来源与信息组织；
第 4—5 页：视觉、页面、修改与质量；第 6—8 页：指标、验收与建设成果。
指标为建议目标，需要本系统实测，不能从参考论文直接套用性能。


<a id="architecture"></a>

## 架构与职责

系统采用工作流编排式多智能体架构，由入口 Router、受控工作流、三个专业 Pi Agent、按需加载的 Skills 和版本化成果组成。

### 三个角色

信息与证据 Agent 提交候选信息和来源；信息设计 Agent 输出 InformationPlan 和 PageSpec；独立审查 Agent 对照原始依据与实际成果，输出 ReviewReport。
每个角色任务使用独立上下文、工具白名单和访问范围，角色之间可以使用同一模型。
会话隔离不是操作系统安全沙箱。

### 控制与实现

Router 识别首次生成、事实更新、展示修改；工作流程序管理依赖、状态、版本与停止条件。
不让主管模型临时改写权限或跳过检查。可选编排框架以后选型，不影响业务成果协议。
Pi SDK 用于后端业务运行层；仅使用 Pi 辅助开发，不能证明业务系统已经接入 Pi。

### 页面与组件

先确定信息组织和页面规格，再实现页面。声明式组件优先复用，但不得套固定企业模板。
当前不直接集成完整 A2UI。组件不足时提交扩展需求，可选组件工程分支在隔离环境处理。
DESIGN.md 仅约束视觉风格，不决定企业事实或硬性栏目。

### 数据与版本

权威业务状态保存在数据库和对象存储中，同时保留事实、资料、设计与页面的版本依赖，不能用模型聊天记录代替。
页面关键元素保留来源入口，候选修改通过检查后才成为新可用版本。

### 部署

代码集中在同一仓库，API、Agent Worker、解析和预览检查服务可分别运行。
三个 Agent 可以共用服务器，系统不自动部署；前端仅访问业务 API。
开发用 Pi CLI、业务 Pi SDK 及其工具和子进程均须在容器或虚拟机内运行，不直接在 Mac 宿主机启动。
开发环境使用 Docker Desktop，项目源码直接挂载到 `/workspace`，Mac 编辑器和 Pi 修改同一份代码；Linux 依赖、运行数据和 Pi 用户目录单独存放。保留普通用户、只读系统和受限 HTTPS 代理；方法与边界见 [容器开发指南](../development/dev-container.md)，验证见 [容器报告（历史记录未随快照上传）](../../SNAPSHOT.md#verification)。业务服务仍未接通。


<a id="agent-contracts"></a>

## Agent 输入输出

Schema 名称与结构为本项目自定义。`packages/contracts` 已实现事实阶段字段与服务层校验；设计与页面协议仍拒绝全部输入，范围见该包 README。

协议固定字段结构、类型、版本和引用规则；企业事实通过主体、属性、值及证据等通用结构表达，属性内容可随资料变化。具体字段与校验由编程 Agent 按方案实现，各模块复用同一份 Schema。候选事实的结构示意与首轮实现范围见 [后端实施指南](../development/backend-plan.md)。

### 共同任务信息

后端提供 taskId、projectId、身份范围、处理阶段、基础版本、目标节点、用户要求、允许修改范围和输入成果引用。企业权限由服务端确定，不能由模型自行决定。
共同输出包含任务与基础版本引用、成果引用，并明确说明资料缺失或任务阻塞的原因。

| 角色 | 输入 | 输出 | 权限边界 |
| --- | --- | --- | --- |
| 信息与证据 | DocumentIR、来源位置、范围、可选旧快照 | 候选 EvidenceSnapshot、变化与冲突 | 提交候选事实，不覆盖可用版本 |
| 信息设计 | 可用事实、目标、全景索引、视觉规范、组件目录；修改时含旧计划与规格 | InformationPlan、PageSpec、ChangeSet；必要时补查或扩展请求 | 只修改设计，不改事实 |
| 独立审查 | 任务、候选成果、原始证据；页面审查包含实际渲染结果，修改审查包含前后差异 | ReviewReport | 不直接修改业务成果 |
| 可选组件工程 | 能力需求、接口、授权代码、测试与隔离限制 | 候选代码、参数、示例、来源与测试记录 | 不改企业事实，不自动部署 |

### 四类核心成果

EvidenceSnapshot：实体、事实、关系、素材、文件与位置、口径、冲突和支持状态。
InformationPlan：受众与目的、内容选择、分组、重点、层级、浏览路径及事实引用。
PageSpec：节点、组件、布局、样式、交互、响应式、数据、事实和素材绑定。
ReviewReport：结果、问题位置、依据、严重程度、建议回退阶段和实际检查记录。

InformationPlan → PageSpec 是同一个设计 Agent 的两层输出，不要求增设 Agent，也不规定固定的调用轮次。
Schema 校验只检查结构，内容正确性还需语义审查；两类检查都必须实现。


### B2 受控读取工具

`runtime/read-document-request` 仅含资料 ID、资料版本 ID 和块 ID；项目及操作权限由可信服务上下文提供。`runtime/read-document-result` 返回同一引用、原文、内容指纹与段落（paragraph）位置。两者由权威 Schema 校验；工具拒绝越权、无效版本、缺失块、未知字段和未支持的位置。

最小验证任务只接受与本次成功工具回执一致的最终 JSON。该结果用于证明受控读取和来源一致性，不是事实抽取候选，也不是独立语义审查报告。


<a id="workflows"></a>

## 工作流程

### 首次生成

上传资料与目标 → Router → 解析 → 信息与证据 Agent → 候选信息快照 →
事实检查 → 信息设计 Agent（InformationPlan → PageSpec）→ 渲染与浏览器检查 →
独立成果审查 → 输出并保存页面版本。

两次审查由同一类角色在独立任务上下文中执行，无需增设角色。
无法判断时明确提示缺失与冲突；正常路径无需逐步人工批准。

### 只调整展示

当前页面版本 + 修改要求 + 选中模块 → 识别范围 → 复用事实 →
必要时更新 InformationPlan，局部修改 PageSpec → 校验变更 → 渲染 →
对照要求与前后差异审查 → 输出新版本。

例如“发展历程改成时间轴，其他不动”：不能改事件日期、事实数量和无关公司简介。

### 更新企业信息

新增资料 + 基础版本 → 只解析变化资料 → 候选事实变化与冲突 → 核验 →
沿依赖关系查找受影响的数据、计算和模块 → 必要时修改设计 → 渲染与检查 → 输出新版本。

只改现有图表中的数据值且结构不变时，不强制重新设计整页。

### 回退与停止

事实问题返回证据处理阶段，组织或布局问题返回设计阶段，解析或渲染故障交由相应服务处理。
程序负责有限重试、预算控制、取消和恢复。候选成果未通过时，不得覆盖原页面。
并发修改需检查基础版本，不能静默覆盖。

### 组件能力不足（可选）

设计提出需求 → 组件工程任务 → 构建、接口、安全、交互与来源检查 →
部署并登记兼容目录版本 → 回到页面设计或渲染；不允许动态运行未审查代码。


<a id="provenance"></a>

## 溯源与版本

页面元素 → 数据记录／派生计算 → 事实版本 → 证据记录 → 原始文件版本及位置。

- 每条关键事实保存主体、时间、单位、统计口径、支持状态和来源，不只保存一个数值。
- 文本片段、图表数据点、关系边均应能映射到事实；不能只在页脚列一份资料表。
- 派生数值保存输入事实和计算规则，程序执行计算，语义审查检查是否超出证据。
- 按 PDF、PPT、Excel、Word 等实际格式保存定位信息；无法定位时明确标注限制。
- 原文件不可被静默替换，旧页面仍使用旧证据版本。
- 用户点击来源后，前端通过带权限校验的证据 API 查询已保存的依据，无需重新请求模型。
- 导出页面需要证据清单与授权附件，或可用的证据服务连接；不能导出后来源失效。

对应代码：parser/source_locator.py、domain/evidence.service.ts、lineage.service.ts、
page-renderer/bindings.ts、api/routes/evidence.ts、web/features/evidence/。


<a id="component-branch"></a>

## 可选组件扩展

代码总结、通用封装和新组件开发是三个不同层次的任务。仅有文字说明，不能认定组件已经可用。
输入来自已有或获授权源码，也可以来自受限组件工程任务；PageSpec 本身不是组件实现代码。

输出应包含接口、实现、用途与限制、示例、来源与依赖、测试和版本。
事实与数据应通过参数传入，不能将某家企业的真实内容作为通用默认值；必须保留 evidenceRefs 等证据接口。

能力验证、隔离构建、客户端部署与目录登记缺一不可；不把未验证代码热加载到所有企业页面。
相关实现位置为 component.workflow.ts、component-engineer/ 和两个组件类 Skills。
