> **文档版本：** 1.0 · 2026-09-29  
> **适用对象：** 项目开发者、前后端协作者、使用 Pi 等工具的编程助手  
> **系统状态：** 本文描述系统方案；事实阶段协议与校验（B1）已实现，业务 Agent、工作流与页面仍待实现，尚不是可运行产品。

本系统基于 Pi Harness，通过工作流编排信息与证据、信息设计、独立审查三个专业智能体，将企业多模态资料转化为可交互、可修改、可追溯的信息展示页面。

## 1. 目标、范围与设计原则

### 1.1 服务对象与最终成果

系统面向企业客户。信息设计范围包括企业介绍、品牌、业务、产品、技术、资质、发展历程、应用领域及其关联，不限于产品目录。

输入包括企业提供的 PDF、Word、PPT、Excel、图片、扫描资料、网页等，以及展示目标、目标受众、品牌规范和允许使用的数据范围。最终范围来自需求书，具体格式支持可以分阶段交付；尚不支持的格式必须明确提示，不能返回成功并静默忽略。[R0，第三至四节](#r00)

正常情况下，系统应输出可交互页面、可查看的事实来源、机器检查结果，以及供后续修改使用的页面版本。系统自主完成主要设计过程，不要求用户手动整理完所有内容后再输入。

### 1.2 核心能力链

```text
资料与任务目标
  → 信息理解与关系发现
  → 信息组织与信息架构
  → 视觉表达和交互设计
  → 页面实现
  → 自动验证与定向修正
  → 可交互、可追溯、可继续修改的成果
```

需求书提出了上述能力要求；Agent 划分、双阶段审查和数据协议由本项目设计，需求书未指定这些程序结构。[R0，第一、六至十节](#r00)

### 1.3 不可退化的要求

| 原则 | 实施时的含义 |
|---|---|
| 内容驱动，而非模板填空 | 信息数量、关系和展示目标能够改变模块、层级、布局与交互；不能每家公司都输出同样的栏目。 |
| 事实优先 | 不把猜测、常识补充、宣传性夸大当作有资料支持的企业事实。 |
| 有关系的信息基础 | 不只为每个文件生成孤立摘要，要关联同一企业、产品、型号、业务、技术和事件。 |
| 设计可以读事实，但不能改事实 | 信息设计 Agent 通过受控工具查询数据，不能直接更新权威事实记录。 |
| 局部修改有约束 | 从当前版本出发理解修改范围，保留已确认内容，不默认重新生成全页。 |
| 溯源贯穿生成 | 页面元素、事实、来源文件版本和具体位置始终关联，不仅在页脚列文件名。 |
| 自动验证后输出 | 审查依靠程序、语义核验与真实浏览器结果；无法判断时明确提示。 |

以上原则对应需求书的事实、设计、迭代和质量要求。[R0，第五至十节](#r00)

### 1.4 首版范围与暂不做的事项

首版必须贯通一个代表性企业的资料理解、设计、渲染、溯源和后续修改。首次数据集应同时覆盖公司基本信息、业务、技术、资质和发展历程中的多个类别，不能用一个无来源的静态主页代替验收。

首版**不默认**建设：自由群聊式协作、全能主管 Agent、独立模型训练、自动安装任意组件、每次输出都人工审批、复杂集群或公网官网发布系统。复杂解析与自动组件工程按阶段扩展，不冒充已覆盖所有格式和设计需求。

## 2. 确定的架构与职责边界

### 2.1 架构名称

**工作流编排式多智能体架构：入口 Router＋受控工作流＋三个专业 Pi Agent＋按需 Skills＋版本化成果。**

三个 Agent 在各自任务中查询信息、调用工具并根据反馈继续处理，外层程序管理依赖和状态。每个角色使用独立上下文，不能在同一会话中依次切换三个提示词来代替；不同角色可以使用同一模型或服务器。

```text
企业用户／页面编辑界面
          │ 资料、目标、修改请求、当前版本
          ▼
API：鉴权、输入校验、创建异步任务
          ▼
Router：规则优先，必要时模型识别请求
          ▼
受控工作流：依赖、权限、预算、检查、回退、版本
          │
          ├── 信息与证据 Agent ──► 候选 EvidenceSnapshot
          │          │                 │
          │          └── 使用信息类 Skills
          │                            ▼
          ├── 独立审查 Agent ──► 事实审查报告
          │                            │
          ├── 信息设计 Agent ──► InformationPlan → PageSpec
          │          │                 │
          │          └── 使用设计 Skills、DESIGN.md、组件目录
          │                            ▼
          ├── 组件渲染器＋浏览器检查服务
          │                            ▼
          └── 独立审查 Agent ──► 成果审查报告
                                       │
                              通过：保存新可用页面版本
                              不通过：定向修正／提示问题
```

图中的两次审查由同一类角色分别执行，使用独立任务上下文。修改任务按变化类型选择所需步骤，无需每次重跑完整流程；用户也无需在节点之间手动复制 Agent 输出。

### 2.2 谁负责什么

| 模块 | 核心职责 | 不应承担的职责 |
|---|---|---|
| Router | 判断首次生成、展示修改、事实更新，识别范围与约束 | 不包办事实提取和页面设计，不动态授予权限 |
| 工作流程序 | 推进阶段、检查前置条件、调用执行者、恢复和提交版本 | 不代替模型作具体的信息设计判断 |
| 信息与证据 Agent | 实体、事实、关系、事件、素材的提取、归并与来源关联 | 不直接覆盖已采用的信息版本，不改页面布局 |
| 信息设计 Agent | 信息组织、视觉表达、布局、交互及规格 | 不改变底层事实值，不编造无依据关系 |
| 独立审查 Agent | 对照证据、约束与实际成果，给出可定位问题 | 不直接修改业务成果，不绕过程序检查 |
| 解析、渲染、存储服务 | 执行确定性处理与受控基础能力 | 不因拥有服务接口就自动成为业务 Agent |

### 2.3 不把 Router 当成第四个核心 Agent

Router 放在 TypeScript 后端。明确界面操作直接按规则分类；自然语言需要理解时可发起一个受约束的模型任务，结果必须由程序复核。

步骤由工作流程序管理，不设长期运行的主管 Agent 反复决策。未来如有明确的动态协调需求，可在局部工作流中评估 Supervisor，但不得因此改变事实和设计的权限边界。当前不要求引入 LangGraph 或任何主管封装库；相关选型留在编排适配层，不传播到业务协议。[方法参考 R11](#r11)

### 2.4 Pi 的位置

Pi 是部署后业务 Agent 的运行时，业务任务必须通过后端 Pi 会话真实执行。开发阶段也可以用 Pi 辅助编程，但仅用于编程不满足本项目的运行时要求。

Pi 官方 SDK 支持嵌入 Node.js 或 Bun 进程并配置会话、模型、工具与资源；本项目将这些调用集中在 `runtime/pi/`，避免业务代码分散依赖 SDK 细节。[R10](#r10)

### 3.3 当前骨架的实际限制

- 后端锁定 Pi SDK 0.99.1，B2 已实现会话、受控读取、预算和取消；`eval:b2` 为显式验收入口，不是 HTTP 服务。目前没有可用的 `pnpm dev`。

- 隔离开发容器、协议与 B2 集成测试已实现；完整业务、页面和 CI/CD 尚未实现，不能当作成功结果。
- 原始需求 PDF、PPT、DOCX 没有复制进骨架；[需求摘要](overview.md#requirements) 是摘要，不是需求全文。

## 4. 数据、成果与统一任务协议

> 本节是对既有协议的**开发细化建议**。字段需要落到 `packages/contracts/schemas/`，经接口确认后实现。示例不是 Pi、A2UI 或参考论文的官方格式。

### 4.1 核心对象

| 对象 | 作用 | 关键约定 |
|---|---|---|
| DocumentIR | 解析后统一的资料表示 | 保留文本、表格、图片、上下文和来源位置，不压成一段纯文本 |
| EvidenceSnapshot | 某版本企业信息与证据快照 | 实体、事实、关系、素材、来源、支持状态与冲突 |
| InformationPlan | 信息架构方案 | 受众、目标、选择与省略、分组、层级、浏览路径、事实引用 |
| PageSpec | 页面规格 | 稳定节点、组件、布局、交互、数据与证据绑定 |
| ReviewReport | 审查结果 | 对应待审版本、实际检查、问题位置、依据与回退建议 |
| ChangeSet | 对当前成果的局部变更 | 基础版本、允许范围、变更操作和影响节点 |
| PageVersion | 某次完整页面输出 | 绑定事实、计划、规格、组件目录、渲染结果与审查报告 |

四类核心业务成果是 EvidenceSnapshot、InformationPlan、PageSpec、ReviewReport；其余对象用于解析、修订和版本管理，无需为它们增设 Agent。

### 4.2 公共任务输入

所有任务至少包含以下信息：

| 字段 | 来源与用途 |
|---|---|
| `taskId`、`attemptId` | 后端生成，区分业务任务与某次执行 |
| `projectId`、`pageId` | 指明当前企业项目与页面；访问权仍由服务端检查 |
| `taskType`、`stage` | 明确任务类型与当前阶段 |
| `userIntent` | 原始用户目标或修改请求，不只保留机器分类结果 |
| `baseVersions` | 修改基于哪组已存成果；首次生成可为空 |
| `inputRefs` | 授权范围内可读取的资料和成果引用 |
| `targetNodeIds` | 用户选定或经复核的目标模块 |
| `constraints` | 事实保留、禁止新增展示事实、不可改节点、品牌等约束 |
| `executionPolicyRef` | 后端受控策略引用，用于工具权限、耗时和预算，不接受模型自授权 |

前端传入的 `projectId` 不能作为授权依据。密钥、原始连接凭据和数据库管理权限不得放入任务提示。

### 4.3 公共输出

Agent 提交的结果应包含输入版本引用、明确状态、候选成果引用、问题和需要的补充输入。状态建议区分：`completed`、`needs_information`、`needs_component`、`blocked`、`failed`。

这里的 `completed` 只表示“本次角色任务完成”，不表示整个页面通过全部验证；`needs_component` 主要用于设计任务，不能拿组件缺失解释事实冲突。

通过 Schema 校验只说明结构符合协议；事实正确性、设计合理性和页面可运行性仍需分别检查。后端可以在接收提交后补充耗时、模型配置、工具执行摘要和校验记录，不要求模型生成自己的审计事实。

### 4.4 事实支持状态与审查状态分开

建议用独立字段表达：

- `supportStatus`：有资料支持、存在冲突、缺少依据或待确认。
- `reviewStatus`：未检查、检查通过、需修正或无法判断。

“有资料支持”不等于现实世界已被证明正确；“经过审查”也不意味着冲突自动消失。人工补充或确认应保存为单独的来源／处理记录，并保留原始分歧。

### 4.5 Schema 与类型只有一个权威来源

以 `packages/contracts/schemas/` 的已确认协议为准，通过脚本生成所需类型与验证代码。字段变化必须版本化并检查前后端兼容；不要让 Python、TypeScript 和提示词各维护一套不同定义。

协议固定结构、类型及引用规则，企业事实的属性与内容可随资料变化。采用主体、属性、值、限定条件和证据等通用表示，避免把全部企业信息写死为少量固定字段；扩展内容同样需要明确约束。具体字段和测试可由编程 Agent 实现，各模块共同复用。首轮示意和任务见 [后端实施指南](../development/backend-plan.md)。

骨架已有 `schemas/agents/`，应分别实现三个核心角色和可选组件角色的输入输出。示例与测试应同时包含合法输入、越权提交、无效引用和版本过期等情况。

## 5. 每个 Agent 的输入、输出与工具

### 5.1 信息与证据 Agent

**任务：回答“资料支持哪些企业信息，它们彼此怎样关联”。**

| 类别 | 明确定义 |
|---|---|
| 输入 | DocumentIR 与素材引用、原始文件版本与位置、待处理范围；更新时加入已有 EvidenceSnapshot 和变化资料 |
| 可查询内容 | 当前项目的原文、表格上下文、图片、既有实体与事实索引 |
| 输出 | 候选 EvidenceSnapshot、事实与关系变更、实体归并说明、冲突与缺失清单 |
| 正常停止条件 | 已处理授权范围内资料，提交结构化成果及未解决问题，不静默丢弃困难内容 |
| 不允许 | 改写当前可用快照、修改页面、将无来源推断写成确定事实 |

拟提供工具：查询资料、读取原文区域、查询现有实体、比较版本、提交候选信息。工具最终调用业务服务；不提供任意 SQL 写入或通用 Shell。工具名由 `evidence.tools.ts` 统一定义。

**处理要求：** 归并时考虑名称、型号、单位、时间、配置和口径。同名不一定指同一对象；两个数值不同也不一定冲突，可能分别表示净重／毛重或对应不同时间。无法确定时保留备选与理由。图片与证书保留素材引用，不用生成图片冒充真实证据。

**实现位置：** `agents/evidence/`、`tools/evidence.tools.ts`、`domain/evidence.service.ts`。

### 5.2 信息设计 Agent

2026-10-20 实施补充：用户要求完善输出协议，已扩展 [PageSpec 1.1](page-spec-v1.1.md) 的布局、视觉、来源内容、状态交互与检查要素，兼容旧版 1.0；新增字段、服务校验及生成类型同步实现。这里只扩展设计候选协议，不把组件、渲染、审查或修订标为完成；下面旧阶段进度以本补充和实际验证报告为准。

**任务：回答“哪些信息应被展示，以及怎样组织、表达和交互”。**

| 类别 | 明确定义 |
|---|---|
| 输入 | 可使用的 EvidenceSnapshot、企业全景索引、展示目标、受众、约束、视觉规范、组件目录 |
| 修改时额外输入 | 当前 InformationPlan／PageSpec、目标节点、基础页面版本、允许与禁止的变化、用户原始要求 |
| 输出 | 首次生成：InformationPlan＋PageSpec；修改：ChangeSet＋更新后的候选成果；必要时：补充信息或组件需求 |
| 可查询内容 | 相关事实、素材、原始证据、设计知识、组件接口与案例 |
| 不允许 | 直接更改事实、编造关系、把未注册组件当作可用实现、绕过页面检查 |

拟提供工具：查询企业信息、读取证据、检索设计规则、查询组件目录、请求渲染预览、提交计划与规格、提交补查／组件需求。设计 Agent 可以根据预览自主修正，之后仍需独立审查。

**InformationPlan → PageSpec 是同一设计 Agent 的两层逻辑成果。** 不要求额外增加两个 Agent，也不规定必须发起两次模型请求。若视觉细化揭示原计划不合理，可返回调整信息组织；变更必须可追踪。

两份产物的字段与绑定细化见 [协议说明](design-contracts-draft.md)。2026-10-11 已按用户同意的样例实现有限 v1 Schema 与服务校验，范围见 [验证记录](../reports/design-contracts-v1-2026-10-11.md)；本节历史示例仍为概念说明，不能代替正式 Schema。设计 Agent 输出规格，下游渲染器生成 HTML，业务 Agent 和渲染器尚未接入。

设计 Agent 先读取企业全景索引，再按需查询细节。不能只依据上一阶段的摘要，也不必把全部原始资料放入上下文。

首次生成的 DesignInput／DesignOutput 及程序校验已补齐，见[接口说明](design-agent-io-v1.md)。当前小任务切片携带完整授权快照，已接入按 ID 读取事实、组件目录与授权段落原文的工具；大快照分页索引尚未实现。独立 Pi 设计会话已通过模拟网关验证，真实模型生成质量尚未验证，也不改变事实阶段公共 Task 枚举。

**实现位置：** `agents/design/`、`tools/design.tools.ts`、`packages/contracts/schemas/`、`packages/page-renderer/`。

### 5.3 独立审查 Agent

**任务：直接对照原始证据、用户要求和实际成果，独立判断生成者的结论是否成立。**

| 审查模式 | 输入 | 输出重点 |
|---|---|---|
| 事实审查 | 候选快照、原始证据入口、口径、差异与冲突 | 事实是否受支持、对象是否对应、来源能否定位、遗漏与冲突 |
| 首次页面审查 | 可用事实、InformationPlan、PageSpec、实际页面及浏览器结果 | 内容是否忠实与完整、组织表达是否合理、布局交互是否正常 |
| 修改审查 | 上述内容＋基础版本、变更集、实际前后差异、修改范围 | 请求是否完成、事实与来源是否保留、无关内容是否被误改 |

`ReviewReport` 建议包含 `verdict`（`pass`、`revise`、`needs_input`）、待审成果版本、每项检查结果、问题节点／事实、证据依据、严重程度和建议返回阶段。字段仍需实现成真实 Schema。

未执行的检查必须标记 `not_run`，不能默认为通过。缺少浏览器检查结果时，审查任务不能宣称响应式检查已通过。审查结论应绑定被检查的确切成果和组件版本，不能拿旧截图审新页面。

拟提供工具：读取原文与事实、查询修改差异、查看页面截图和交互结果、运行允许的检查、提交报告。审查角色只能提交检查成果，无权修改企业事实或 PageSpec。

**实现位置：** `agents/review/`、`tools/review.tools.ts`、`domain/result-validator.ts`。

### 5.4 可选组件工程 Agent

输入是组件能力需求、授权源码、接口约束、合成测试资料和隔离策略；输出是候选代码、接口规范、用途限制、示例、依赖来源和测试记录。它不修改企业事实，不自动部署到所有页面。仅在第 14 节的分支中启用。

### 5.5 角色权限表

| 能力 | 信息与证据 | 信息设计 | 独立审查 | 可选组件工程 |
|---|---|---|---|---|
| 读取当前项目授权证据 | 是 | 按任务需要 | 是 | 默认否，优先使用合成数据 |
| 提交候选事实 | 是 | 否，可提出补查请求 | 否，可指出问题 | 否 |
| 提交 InformationPlan／PageSpec | 否 | 是 | 否 | 否 |
| 提交审查报告 | 仅自检信息，不代替独立审查 | 同左 | 是 | 仅工程测试记录 |
| 修改组件源码 | 否 | 否，可提出需求 | 否 | 仅候选隔离工作区 |
| 更新当前可用版本指针 | 否 | 否 | 否 | 否 |

最后一项由工作流与业务服务执行。以上权限必须通过实际工具与服务校验实现，不只写在提示词中。

## 6. InformationPlan 与 PageSpec 的具体例子

### 6.1 两层分别解决什么

| 对象 | 回答的问题 | 不该代替什么 |
|---|---|---|
| InformationPlan | 展示哪些内容、为什么、怎样分组、谁先谁后、怎样浏览 | 不直接决定每个 CSS 属性 |
| PageSpec | 用何种表达、如何布局和交互、调用什么能力、绑定什么数据 | 不能凭空增加企业事实 |
| DESIGN.md | 整体配色、字体、间距、密度和风格约束 | 不固定本次必须有多少栏目 |

这一分层对应需求书的信息组织与视觉设计要求，并参考 ViviDoc 的结构化规格、DataNarrative 的规划后细化方法。**两层名称与拆分由本项目定义**，不是直接引用某篇“PageSpec 论文”。[R0，第六至七节](#r00) [R1](#r01) [R7](#r07)

### 6.2 信息架构示例

以下公司、编号、数据集均为说明用的**假设示例**。

任务：“向合作伙伴说明公司的业务、技术支撑和发展过程。”

InformationPlan 可以决定：

```json
{
  "schemaVersion": "0.1-draft",
  "planId": "plan_example_v1",
  "evidenceSnapshotRef": "evidence_example_v1",
  "audience": "潜在合作伙伴",
  "goal": "理解业务与技术的关联及其形成过程",
  "sections": [
    {
      "sectionId": "business_technology",
      "question": "公司做什么，依靠哪些技术？",
      "organization": "业务关联支撑技术和应用场景",
      "claimRefs": ["claim_relation_01", "claim_relation_02"]
    },
    {
      "sectionId": "company_history",
      "question": "这些业务和技术如何逐步形成？",
      "organization": "选择与当前能力相关的事件并按时间排列",
      "claimRefs": ["claim_event_01", "claim_event_02"]
    }
  ],
  "browseOrder": ["business_technology", "company_history"]
}
```

该示例先确定叙述目标、内容关系和浏览顺序，不预选固定企业模板。实际字段需补充完整性检查、内容省略理由等约定，不能将本示例直接当作完成的 Schema。

### 6.3 页面规格示例

同一方案中的发展历程模块可细化为：

```json
{
  "schemaVersion": "0.1-draft",
  "pageSpecId": "spec_example_v1",
  "informationPlanRef": "plan_example_v1",
  "evidenceSnapshotRef": "evidence_example_v1",
  "componentCatalogRef": "catalog_example_v1",
  "themeRef": "brand_example_v1",
  "nodes": [
    {
      "nodeId": "company_history",
      "planSectionId": "company_history",
      "component": "Timeline",
      "dataRef": "history_dataset_example_v1",
      "props": {
        "title": "企业发展历程",
        "order": "ascending"
      },
      "responsive": {
        "small": "vertical",
        "large": "horizontal"
      },
      "actions": {
        "itemClick": "openEvidence"
      }
    }
  ]
}
```

每条事件数据继续携带事实引用。`openEvidence` 是拟实现的受控操作，不是可直接注入的任意 JavaScript。渲染器按事件记录查询来源，不让模型重新搜索出处。

该例只有一个节点，是协议说明，不代表完整企业页面必须只有时间轴。不能把动态设计能力简化为总是更换同一组件的文字。

## 7. Router 与任务分类

### 7.1 输入与输出

输入：用户原始要求、可选新增文件、当前页面与事实版本、选中的节点、当前任务状态和权限范围。

输出：任务类型、变化层次、目标节点、需处理资料、保留约束和基础版本。Router 只提议处理路径；工作流校验后才执行。

| 类型 | 典型请求 | 路径 |
|---|---|---|
| 首次生成 | “根据这些资料生成公司展示页面。” | 完整生成链路 |
| 视觉与交互修改 | “历程改成时间轴，其他不动。” | 复用事实，局部修改 PageSpec |
| 信息组织修改 | “突出技术优势，但不要增加事实。” | 复用事实，调整计划与规格 |
| 企业信息更新 | “根据新统计表更新研发人数。” | 资料与事实更新，再更新影响内容 |
| 整体目标变化 | “从公众介绍改成面向合作伙伴。” | 复用事实，允许更大范围重组设计 |
| 混合修改 | “补充今年的事件，并改成时间轴。” | 先核验新事实，再进行设计修订 |

“有新文件”不一定等于事实更新：新文件也可能是视觉参考。文件用途不明确、目标对象不明确或资料口径冲突时，应提出具体澄清问题，而不是猜测后覆盖成果。

### 7.2 路由结果示例

```json
{
  "taskType": "revise_page",
  "changeKinds": ["presentation"],
  "targetNodeIds": ["company_history"],
  "baseVersions": {
    "page": "page_v5",
    "evidence": "evidence_v3",
    "informationPlan": "plan_v2",
    "pageSpec": "spec_v5"
  },
  "constraints": {
    "preserveFactValues": true,
    "allowNewDisplayedClaims": false,
    "allowedNodeIds": ["company_history"]
  }
}
```

`preserveFactValues` 和 `allowNewDisplayedClaims` 不能合并：不改已有值，并不自动禁止向页面添加另一条事实。程序必须根据请求分别检查。

### 7.3 Router 不重复审批每一步

一次分类结果在当前有效版本内使用。每步完成后由状态机推进；只有出现新需求、版本冲突或处理范围实质变化时才重新判断。规则已经明确时，无需再调用模型。

## 8. 首次生成流程

| 阶段 | 执行者 | 输入 → 输出 |
|---|---|---|
| 1. 建立任务 | API、Router、工作流 | 上传资料与目标 → 任务、资料版本、授权与预算 |
| 2. 解析资料 | Python 解析服务 | 文件版本 → DocumentIR、素材及解析质量信息 |
| 3. 整理信息 | 信息与证据 Agent | 解析资料＋索引 → 候选 EvidenceSnapshot |
| 4. 核验事实 | 程序＋独立审查 Agent | 候选快照与原文 → 可用信息版本或待解决问题 |
| 5. 信息设计 | 信息设计 Agent | 可用事实＋目标＋设计资源 → InformationPlan → PageSpec |
| 6. 实现与观察 | 组件渲染器、浏览器服务 | PageSpec＋数据＋组件版本 → 页面、截图、交互检查 |
| 7. 成果审查 | 程序＋独立审查 Agent | 原始依据、设计、实际页面 → ReviewReport |
| 8. 保存输出 | 工作流与版本服务 | 审查合格的同一组成果 → 新可用页面版本 |

设计或审查发现遗漏时，可提出补查请求，由工作流返回证据阶段。发现组件能力缺口则走可选工程分支或输出明确阻塞，不返回一个缺失所需表达的“成功页面”。

**正常路径自动输出，不增加人工发布审批。** 无法判断的关键事实与不能自动解决的错误需要提示；可允许用户查看明确标注的候选草稿，但不能把它标为已验证最终成果。双阶段审查是本项目安排，不直接声称来自 ViviDoc。[R0，第十节](#r00)

## 9. 后续页面修改与企业信息更新

### 9.1 修改从当前页面开始

修改请求至少包含当前 `pageVersionId`、原始要求、目标节点和可选新增资料。前端的“选中模块再提问”需要使用稳定节点 ID，不能只依赖屏幕坐标或相似标题。

```text
当前页面版本＋修改要求＋可选资料
                 ↓
Router 分类，工作流校验范围和基础版本
                 ↓
       是否涉及企业事实变化？
        ├─ 是：处理变化资料 → 候选事实 → 核验
        └─ 否：复用原事实版本
                 ↓
沿依赖关系确定影响内容
                 ↓
必要时调用设计 Agent 更新计划／规格
                 ↓
检查变更范围 → 渲染 → 浏览器检查
                 ↓
独立审查：完成要求＋保留事实＋无关内容未误改
                 ↓
通过：提交新页面版本；失败：修正或保留原版并提示
```

只有相关事实变化时才重新运行证据整理，不重复解析未变化的所有文件。但最终页面审查仍需核对被改写的表述和引用，不能把“没有更新事实库”误认为“页面没有事实错误”。

### 9.2 纯展示修改

例：“把公司发展历程改成时间轴，其他内容不要动。”

工作流读取原事件、来源、当前计划与模块规格。若内容选择、顺序与浏览路径不变，可复用 InformationPlan；设计 Agent 仅修改相关 PageSpec 节点。通过后生成新页面版本，继续绑定原事实快照。

检查要点：日期与事件未变、来源仍可点击、无关模块未改、时间轴交互正常、移动端与相邻布局无回归。局部修改并不等于只看一个局部截图。

### 9.3 信息组织修改

例：“突出技术优势，但不要增加新的事实。”

允许调整已展示内容的优先级、组合与呈现，必要时修改 InformationPlan，再同步 PageSpec。是否可以从既有事实库添加此前未显示的信息，必须依据用户约束判断，不能擅自扩大解释。

设计 Agent 提交变更依据；程序检查所引用事实集合和实际页面内容，审查 Agent 检查语义是否被夸大。不能把“有十二项专利”改写成没有依据的“技术行业第一”。

### 9.4 企业信息更新

例：“根据新资料更新研发人数。”

只解析变化资料，信息与证据 Agent 比较主体、统计日期、单位与口径。核验形成新的候选信息版本后，由 `impact-analysis.ts` 沿依赖找出受影响的数据点、派生值、文本、关系与模块。

如果只是已有图表中的数值变化，设计仍适用，可以由数据绑定与渲染完成更新，不强制再次调用设计 Agent。如果新增业务、关系或内容数量改变信息结构，再调用设计 Agent 调整计划和规格。

**事实变了不代表旧资料无效。** 新旧资料与页面分别固定到各自版本；未更新页面不得在用户不知情时自动改用新数值。

### 9.5 混合请求与范围扩展

“补充今年事件，并把历程改成时间轴”必须先核验事件，再设计展示。若系统认为还要改动用户未允许的模块，应说明影响并请求扩大范围；不能用“优化效果”作为越界修改的理由。

对于“整体换成面向投资伙伴的介绍”等明确全页目标变化，可以重组全页设计，但不重新提取未变化资料，也不自动补充外部事实。

### 9.6 ChangeSet 的要求

变更集以稳定节点和基础版本为对象，记录目标、修改前置条件、操作、数据／事实引用变化及影响范围。具体 patch 格式可在实现时确定，不预设所有修改都用字符串替换。

应能根据基础版本与合法变更集重建完整候选成果，并检查重建结果是否一致。程序还必须检测 ChangeSet 未申报的变化，不能只依赖模型对修改范围的说明。

### 9.7 删除资料和用户直接改数字

删除或撤回资料前，需要分析对已有证据的影响，避免来源断链或相关结论被静默删除。资料保留和删除策略应在授权范围内明确。

用户直接输入新的事实值时，把它保存为可识别的用户陈述或更正请求，不能伪造为来自原 PDF 的值。需要进一步证据时明确提示，确认记录保留时间、对象和理由。

## 10. 版本、状态、重试与提交

### 10.1 页面版本固定完整依赖

PageVersion 至少绑定以下内容：

```text
pageVersionId
  ├─ EvidenceSnapshot 版本
  ├─ InformationPlan 版本
  ├─ PageSpec 版本
  ├─ 数据集、派生计算和素材版本
  ├─ 组件目录、渲染器和视觉规范版本
  ├─ 渲染成果与浏览器检查结果
  └─ ReviewReport 及待审成果指纹
```

“同一个组件名称”不等于“同一个实现”。组件版本升级后，旧页面也应能确定使用哪个版本，不能用一份旧报告证明任意新渲染器输出正确。

### 10.2 建议的状态分类

任务状态可包含 `queued`、`running`、`waiting_for_input`、`waiting_for_component`、`succeeded`、`failed`、`cancelled`、`superseded`。具体执行阶段另放 `stage`，避免把阶段名称与任务终态混在一起。

成果状态分别管理“候选、可用、未通过”，不要把 Agent 返回 `completed` 直接映射为页面可用。等待补充时记录可恢复的阶段、问题和输入版本，不让 Worker 无限制占用会话空等。

### 10.3 失败按原因处理

| 问题 | 处理方式 |
|---|---|
| 网络或外部服务暂时失败 | 有上限的技术重试；复用已完成的有效阶段 |
| Schema 不合法 | 返回明确字段错误，让相应执行者定向修正 |
| 来源或数值错误 | 返回证据处理或事实表达修正，重新执行有关检查 |
| 信息组织或布局不合理 | 返回设计阶段；不能顺便改事实 |
| 解析或浏览器运行失败 | 定位到相应服务，不能让评审模型假装已检查 |
| 关键冲突、缺失依据 | 提示用户补充，保留备选与可信状态 |
| 组件不支持设计意图 | 显式阻塞或进入受控组件分支 |
| 基础版本过期 | 拒绝静默提交；重新读取差异、重建候选并重新审查 |
| 达到预算或修正上限 | 停止并报告已完成部分、限制和下一步所需输入 |

技术重试和语义修正计数应区分。具体调用预算、并发数和修正上限通过配置与实测确定，不在本文虚构“最佳”数值。

### 10.4 提交不覆盖当前可用成果

建议提交过程为：保存候选文件 → 程序校验 → 完成必要审查 → 检查基础版本仍有效 → 在受控事务中登记 PageVersion 并更新当前指针。

模型无权直接更新当前指针。发生并发修改时，不允许后完成任务无条件覆盖先完成结果。队列重复投递或网络中断恢复，也不能插入重复事实、重复发布同一版本；阶段提交需有幂等标识和重复检测。

对于已保存的新事实但尚未完成页面更新的情况，旧页面仍绑定旧快照。不能先把旧页面的数据指针改掉，再声称后续审查会补上。

### 10.5 回滚与恢复

回滚选择一组历史成果与兼容实现，不重新请求模型“还原”旧页面。原始快照与证据仍可查看。旧组件因安全问题不能继续执行时，应提示并通过受控迁移重新验证，不强行运行有问题的历史代码。

取消应传播到 Pi 会话、解析／浏览器任务和队列状态；已完成的候选产物可以留作诊断，但取消任务不得再提交新的可用版本。

## 11. 页面可溯源的完整实现

### 11.1 一条贯穿全流程的数据链

```text
最终页面版本中的具体元素
  → 绑定的数据记录、文本片段或关系边
  → 事实版本／派生计算
  → 证据记录
  → 原始资料的固定版本＋具体位置
```

用户点击来源后，API 查询已保存的溯源链路，无需再发起问答或让模型重新寻找来源。[需求依据 R0，第五节](#r00)

### 11.2 最小事实记录示例

以下为虚构示例，字段是拟定义的数据协议：

```json
{
  "claimId": "claim_rnd_2025",
  "claimVersionId": "claim_rnd_2025_v1",
  "entityId": "company_example",
  "predicate": "rnd_headcount",
  "value": {"type": "number", "normalized": 60, "unit": "人"},
  "qualifiers": {"year": 2025, "basis": "年末在岗研发人员"},
  "supportStatus": "supported",
  "reviewStatus": "pending",
  "evidenceRefs": ["source_rnd_table_v1"]
}
```

相应证据记录必须能说明：固定的文件版本、工作表“研发”、数值单元格 B4，以及年份、表头、统计口径所在的关联区域。一个孤立的“60”不构成完整语义依据。

事实的逻辑编号与事实版本编号分开；同一对象随时间变化、同一字段纠错、同一事实追加来源，是不同情况，不能一律通过覆盖同一个值来处理。

### 11.3 不同格式的定位

| 资料格式 | 拟保留的定位信息 |
|---|---|
| PDF | 文件版本、页序号、页面区域或内容块、必要上下文；坐标体系和页序号规则统一 |
| PPT | 文件版本、幻灯片序号、对象或文本块；有需要时关联该版渲染区域 |
| Excel | 文件版本、工作表、单元格／区域、表头、单位；涉及公式时保留相关表达和输入 |
| Word | 文件版本、段落／表格／图片等结构位置；需要页码时关联固定的渲染版本，不依赖可变分页 |
| 图片与扫描件 | 原图版本、区域、识别内容与处理来源；无法可靠识别时标注限制 |
| 网页 | 授权采集的内容快照、采集时间、原始地址和结构定位；原站变化不替换旧证据 |

以上是需要落实的格式适配要求。Docling 提供统一文档表示与可获得的结构、来源信息，但不能据此宣称所有格式的区域定位已达标；每类样本都必须实际验证。[R5](#r05)

### 11.4 页面元素怎样保留引用

图表的每个数据记录携带对应事实引用；关系图的每条边引用关系事实；有事实含义的文本保留段落或片段级引用。纯布局、标题装饰等非事实元素不用伪造证据。

关键数值通过数据绑定读取已核验记录，不由设计 Agent 手工复写。文本可以概括，但必须保留依据，并检查主体、时间、单位和因果含义是否保持一致。

### 11.5 派生计算怎样追溯

例如根据 2023 年 40 人与 2025 年 60 人计算增长 50%，需先确认两年的统计口径可比。保存输入事实版本、计算方法 `(60-40)/40`、单位和结果，由程序执行计算。

点击派生值时，展示输入依据与计算过程；不能把计算结果伪装成原文件直接给出的数值。自然语言总结还需语义核验：研发人数增加不自动证明“行业领先”。

### 11.6 前端证据面板

用户点击来源标记、图表数据点或关系对象时：

```text
界面触发 openEvidence
  → 带页面版本和事实／数据记录引用查询 API
  → 后端校验当前用户对该项目与来源的权限
  → 返回事实、支持状态、文件版本、摘录和定位信息
  → EvidencePanel／SourceViewer 显示并定位原始依据
```

权限不足时显示受限说明，不泄露未授权摘录或签名链接。页面能够公开展示不等于原文件必须公开。导出页面时，需要明确采用“连接授权证据服务”还是“随包提供获授权的证据清单与附件”；只有页面 HTML 不能保证离线溯源。

### 11.7 溯源的代码落点

| 路径 | 职责 |
|---|---|
| `services/parser/src/source_locator.py` | 原始位置与上下文 |
| `apps/server/src/domain/evidence.service.ts` | 事实、来源、冲突和快照 |
| `apps/server/src/domain/lineage.service.ts` | 依赖与证据查询 |
| `packages/page-renderer/src/bindings.ts` | 元素、记录与事实绑定 |
| `apps/server/src/api/routes/evidence.ts` | 有权限的来源接口 |
| `apps/web/src/features/evidence/` | 证据面板与原文定位 |
| `packages/ui-components/src/evidence/` | 可复用来源标记和抽屉 |

**验收必须真正点击到对应原文。** 存在一个 `sourceRefs` 字段、或 Agent 回答“来源可靠”，都不是溯源功能完成的证明。

## 12. 声明式渲染与组件库

### 12.1 页面主路径

2026-10-21 实施：已增加 [离线 HTML 预览适配器](../../packages/page-renderer/README.md)，校验 PageSpec 1.0/1.1 后输出可直接打开的页面，支持受控交互及获准导出的证据摘录。它保持声明式主路径；React 应用、完整证据 API、独立页面审查与最终采纳尚未完成，不能把预览标为已验证发布成果。

```text
InformationPlan → PageSpec
                    ↓
           协议、引用与组件能力校验
                    ↓
           数据绑定＋组件注册映射
                    ↓
           已实现的前端组件运行
                    ↓
           可交互页面＋来源入口
```

这借鉴 A2UI 的“界面描述与客户端实现分离”，不代表 PageSpec 已经兼容 A2UI。若后续直接使用 A2UI，应选择协议与组件目录版本，增加转换与兼容性测试；不能将自定义 JSON 直接当作 A2UI 消息。[R4](#r04)

### 12.2 组件不是静态素材

素材是企业图片、标识、证书等；组件是接收数据与配置、执行布局和交互的前端程序；DESIGN.md 是视觉规则。三者分别管理。

现有骨架按 React／TypeScript 预留组件和渲染入口，具体图表库尚未选定。Agent 生成规格，开发者实现组件；并非每次都把模型输出的 JSON 再交给模型翻译成代码。

| 已有占位组件 | 计划支持的能力 |
|---|---|
| `Section`、`ResponsiveGrid` | 结构分组与可组合布局 |
| `BarChart`、`LineChart` | 可比数量、趋势和数据点交互 |
| `Timeline` | 时间事件、展开和来源查看 |
| `RelationExplorer` | 业务、技术、应用等关系与联动 |
| `ComparisonMatrix` | 同口径对象的属性比较 |
| `SourceBadge`、`EvidenceDrawer` | 来源标记与证据展示 |

这些文件目前是占位，不是已实现组件。后续针对技术流程、更多关系或特殊交互扩展，不应因首版目录里没有就删掉需求。

### 12.3 组件目录应说明能力边界

每个组件应有名称、版本、接口 Schema、数据条件、适用与不适用场景、支持的交互、响应式行为、证据绑定方式及测试示例。

前端注册表与 Agent 可见目录必须匹配。组件名称存在但实现尚未部署时，应明确报告能力缺失，不得生成假截图或用空组件代替。A2UI 的自定义组件机制也区分接口定义、客户端实现和注册；本项目参考这一约束，不照搬其全部框架。[R4](#r04)

### 12.4 不允许组件反过来决定企业结构

设计顺序必须是内容与目标 → 信息组织 → 视觉表达 → 实现能力匹配。不能先挑固定企业主页模板，再把所有信息压缩成它能填的几个字段。

组件覆盖需求时优先复用；覆盖不足时比较已有可组合方式与扩展需求。无法保留必要语义的替代方案必须明确提示，不得暗中把关系图降级成无关联的列表。

### 12.5 页面交互与模型调用分开

筛选、展开、切换视图、图表联动和查看已绑定证据，优先由前端状态与受控 API 完成，不每次调用大模型。自然语言设计修改或资料更新才启动相应工作流。

PageSpec 只允许已定义的操作和表达，不把任意 JavaScript、任意 URL 请求或动态包安装嵌入配置。需要新可执行能力时走组件工程，而不是运行未审查代码。

### 12.6 速度与质量的评价

组件复用旨在减少重复的界面开发工作，实际加速效果仍需验证。记录首次可预览时间、完成所有检查的总时间、局部修改耗时、模型调用和重试次数；不能因为流式输出已显示页面框架，就认定最终生成已完成。

## 14. 可选的组件提炼与扩展分支

### 14.1 目标与启用条件

分支处理三个层次：理解已有组件、将专用代码提炼为通用组件、按明确需求编写新组件。它不是每次生成页面都执行的第四个核心角色。

骨架预留 `APP_ENABLE_COMPONENT_ENGINEERING=false`。实现时严格解析布尔值，不把非空字符串 `"false"` 当作启用。首版默认关闭；未启用时返回能力缺口和所需人工开发项。

### 14.2 输入、输出与步骤

```text
设计提出能力缺口／开发者提供授权源码
  → 组件工程任务读取接口与约束
  → 理解、参数化或开发候选代码
  → 构建、接口、安全、布局、交互及溯源测试
  → 登记候选版本与测试证据
  → 经工程交付流程部署兼容实现和组件目录
  → 返回设计／渲染任务继续执行
```

输入来源必须是已有或获授权的源码，或明确受控的新开发任务。**PageSpec 本身不是组件实现代码**；总结一个页面规格不会自动得到一个可运行组件。

输出至少含代码、参数 Schema、用途与限制、示例、来源与许可登记、依赖、测试和版本。组件接口与实际实现必须一致。

### 14.3 事实与来源不能在组件提炼中丢失

例如将企业专用的“业务—技术—应用”视图提炼为 RelationExplorer，应把节点、关系、主题和证据映射变成输入参数，不把某家企业的真实数据写成默认值。

代码总结、测试通过、客户端已部署是三个不同状态。候选代码不能直接热加载到全部企业页面。工程部署检查不等于为每次页面生成增加人工内容审批。

## 15. 后端接口、存储与前端交互

> 本节给出**拟实现的接口和逻辑实体**，用于补全现有骨架。不是已经上线的 API，不承诺当前路径可调用。

### 15.1 核心 API 契约

接口统一放在业务 API 下，所有读取与写入都检查企业项目权限。

| 接口示例 | 输入／输出 | 代码落点 |
|---|---|---|
| `POST /api/projects/{projectId}/documents` | 上传文件或创建上传凭证，返回资料版本与状态 | `api/routes/documents.ts` |
| `GET /api/projects/{projectId}/documents` | 资料、版本、解析与来源定位状态 | `api/routes/documents.ts` |
| `POST /api/projects/{projectId}/tasks` | 创建首次生成或资料更新任务，返回任务 ID | `api/routes/tasks.ts` |
| `GET /api/tasks/{taskId}` | 当前状态、阶段、成果引用、问题 | `api/routes/tasks.ts` |
| `GET /api/tasks/{taskId}/events` | 经过筛选的进度事件流 | `api/routes/tasks.ts` |
| `POST /api/tasks/{taskId}/cancel` | 发起取消，返回可确认的状态 | `api/routes/tasks.ts` |
| `POST /api/pages/{pageId}/revisions` | 基础版本＋修改要求＋节点＋资料，返回修订任务 | `api/routes/pages.ts` |
| `GET /api/pages/{pageId}/versions` | 历史版本与验证状态 | `api/routes/pages.ts` |
| `GET /api/pages/{pageId}/versions/{versionId}` | 精确版本的规格、绑定和可访问预览 | `api/routes/pages.ts` |
| `GET /api/pages/{pageId}/versions/{versionId}/evidence` | 按节点／数据记录／事实查询来源 | `api/routes/evidence.ts` |
| `POST /api/pages/{pageId}/restore` | 恢复授权的兼容历史版本并记录操作 | `api/routes/pages.ts` |

项目创建、成员管理等通用接口需要时再补，不把它们混入 Agent 工具循环；骨架中的前端项目页面目前也只是占位。

长任务返回任务 ID 后异步执行，不把全流程放在一个无限等待的 HTTP 请求里。可以用 SSE 或 WebSocket 推送进度；具体方式在实施时统一选择。

### 15.2 状态事件与页面交互

事件可以包括 `task_started`、`stage_started`、`artifact_created`、`review_completed`、`needs_input`、`completed`、`failed`、`cancelled`。这些是本项目可定义的用户可见事件，不直接泄露原始提示、完整工具参数、敏感资料或内部推理。

浏览器内的普通筛选和展开不用创建生成任务。用户提出“修改布局”时才发送修订请求；用户查看来源时直接查证据 API。

用户补充输入后，后端检查等待任务的基础版本是否仍有效，再决定恢复、重建候选或提示版本冲突，不能无条件续写旧页面。

### 15.3 逻辑存储实体

建议以 PostgreSQL 管理结构化业务记录，对象存储保存原文件、素材、解析产物、截图和页面成果。本地开发可先使用骨架预留的本地存储驱动，后续通过同一存储接口切换，不把 Mac 绝对路径写进业务协议。

| 实体类别 | 内容 |
|---|---|
| 项目与访问控制 | 企业项目、用户或服务身份、授权范围 |
| 资料与解析 | 文档、不可变文档版本、解析产物、素材与位置 |
| 信息与证据 | 实体、事实版本、关系、证据、冲突、快照成员 |
| 数据与计算 | 数据集版本、行记录、派生计算输入与方法 |
| 设计与页面 | InformationPlan、PageSpec、ChangeSet、PageVersion |
| 检查与执行 | 任务、阶段尝试、工具审计摘要、ReviewReport、浏览器检查 |
| 组件与依赖 | 组件目录、实现版本、引用关系和兼容性记录 |

这不是要求立刻创建同名数据库表。具体关系模式、索引和迁移脚本在实现前审阅；首版不强制使用图数据库，但实体关系和依赖仍需可查询。

### 15.4 前端至少提供的功能

资料上传与状态、任务进度、当前可用页面、节点选择与自然语言修改、版本比较与恢复、事实来源查看、冲突和未完成检查提示。

预览应使用相同的组件和绑定规则；不能让审查环境检查一套页面、用户最终看到另一套未验证实现。候选预览与已验证版本标识分开。

## 16. Pi 接入、本地开发与部署

### 16.1 运行方式

代码放在同一仓库，API、Agent Worker、Python 解析和浏览器预览检查在逻辑上分开。可按需要使用独立进程或容器，不要求三个角色各占一台服务器。

用户于 2026-10-03 明确要求：开发用 Pi CLI、包含 Pi SDK 的业务执行进程，以及它们调用的工具和子进程，都在容器或虚拟机内运行，不直接在 Mac 宿主机启动。2026-10-07 已建立并验证 Mac Docker Desktop 开发环境；业务服务仍待实现。

```text
Mac 上的浏览器
   → 本地 Web 前端
   → TypeScript API
   → 队列／工作流 Worker（Pi 执行进程位于隔离环境）
       → Pi SDK：三个专业会话
       → Python 解析服务
       → 渲染与浏览器检查
   → 数据库＋文件存储
```

后端优先按现有 Node.js／TypeScript 方向实施；Bun 是 Pi SDK 支持的另一种宿主，并不要求同时维护两套运行方式。具体 SDK、Node、Python 和包管理器版本在实施前核对并锁定。[R10](#r10)

### 16.2 Pi 适配层要实现的事情

| 文件 | 实现要点 |
|---|---|
| `session-factory.ts` | 以角色配置创建会话；明确模型、资源、工具与工作区；任务结束释放；不默认继承不必要的个人配置 |
| `skill-loader.ts` | 只提供允许的、审核过的技能与参考；不扫描上传资料作为技能 |
| `event-bridge.ts` | 订阅运行事件，转换为任务进度与诊断，不将秘密回传前端 |
| `execution-limits.ts` | 全局和阶段预算、取消传播、超时、工具失败与停止条件 |

B2 固定读取任务已通过真实模型工具验收，工具协议位于 `schemas/runtime/`。B3 已在同一运行层实现首次生成的段落资料提取、候选校验、内存保存和一次结构修正；提取与归并 Skills 从固定仓库路径作为角色指令载入，不扫描上传目录。真实提取质量尚未验收，独立审查、增量更新与持久保存仍待后续阶段，详见 [B3 本地实现报告（历史记录未随快照上传）](../../SNAPSHOT.md#verification)。

专业 Agent 不共享一份无限增长的聊天记录。跨阶段使用已存成果；恢复会话时核对任务和成果版本。Pi 会话日志只用于执行上下文与诊断，不作为企业权威事实库。

### 16.3 模型接入与测试

2026-10-08 初步选用 DeepSeek，通过用户提供的第三方网关接入。当前开发配置采用该平台模型列表返回的 `deepseek-v4.1-flash`，作为首轮验证候选；具体型号和能力以平台实际支持及验证结果为准，不能将开发 CLI 的配置视为业务 SDK 已接通。

模型通过配置接入，首轮必须验证实际接口的工具调用、结构化结果和视觉输入能力。不同角色可以使用同一模型，之后根据真实评测决定是否分配不同模型。

没有配置模型凭据时明确失败或进入显式测试模式，不能自动返回假快照、假页面或“审查通过”。测试可使用 mock，但结果与真实模型执行必须分别标记。

后端在本地运行时，仍可能调用外部模型。必须明确哪些文字、表格、图片和证据片段允许发送，模型 API 密钥只在服务端使用。

### 16.4 当前环境变量

骨架 `.env.example` 已预留 `APP_API_HOST`、`APP_API_PORT`、`APP_WEB_ORIGIN`、`APP_PARSER_URL`、数据库与队列地址、本地存储、会话目录、模型配置和组件工程开关。B2 的 `config/env.ts` 已显式读取 `APP_MODEL_*`；验收入口还读取 `APP_RUN_LIVE_EVAL` 与可选 `APP_B2_REPORT_PATH`，不自动加载 `.env`。其余服务变量尚未接入。

其中示例端口为 API `3001`、前端 `5173`、解析 `8001`，只是可修改的本地约定，不表示这些服务已经运行。

`APP_MODEL_*` 是本项目配置字段，不是 Pi 官方环境变量名。`config/env.ts` 负责读取和校验，再由 Pi 适配层映射到选定版本的真实 SDK 接口。不要在前端暴露模型密钥。

相对路径统一按项目根目录解析，而不是随着 Worker 的当前工作目录变化。运行数据放 `.local-data/` 等被 Git 忽略的位置，不放 `src/`。

### 16.5 Mac 上开发，Pi 在隔离环境执行

2026-10-08 按用户要求简化开发流程：Mac 项目根目录直接读写挂载到容器 `/workspace`，编辑器和 Pi 操作同一份源码，Git 拉取和文件修改实时可见，不再复制源码或导出同步。开发用 Pi、SDK、工具和测试仍在 Docker Desktop 的 Linux 容器中运行。Git 元数据只读提供给容器以查看分支和差异，提交与推送在 Mac 上完成。

Linux 的 `node_modules`、容器运行数据及 Pi 用户目录分别使用命名卷，避免混用 Mac 依赖并遮蔽宿主 `.local-data` 中的本地配置。启动时从镜像缓存离线安装锁定依赖；依赖变化后重新构建镜像。容器使用普通用户、只读系统文件、禁止提权和资源限制，不共享个人主目录、SSH 凭据或 Docker socket。Pi 可直接修改、删除共享项目里的源码，这一范围内的变更通过 Git 检查和管理。

开发容器仅接入没有默认外联路由的内部网络，HTTPS 请求经独立 Squid 代理按域名白名单放行，拒绝内网、回环和链路本地地址。模型配置和 API 密钥由用户在 Git 忽略的本地配置目录填写；密钥会提供给容器内进程，因此工具也可能读取它。当前不发布宿主端口；模型、浏览器预览和业务服务需分别完成配置与验证。使用方法见 `docs/development/dev-container.md`，实际检查见 `docs/reports/dev-container-verification.md`。业务 Dockerfile 仍为占位。

长期多人访问时再部署独立环境；路径、端口、存储、凭据和模型端点均配置化。注意目标架构与依赖兼容，不能把 Mac 生成的本地二进制直接假定为 Linux 可用。

**不要在本阶段自动购买服务器、启用公网入口、安装系统级后台服务或把用户个人主目录挂载给业务 Agent。**

## 17. 安全与数据边界

Pi 官方说明，执行能力继承启动进程权限；工作目录、独立会话和项目可信配置都不是完整安全沙箱。[R10：Security](#r10)

本项目必须在服务层落实以下边界：

| 边界 | 要求 |
|---|---|
| 企业隔离 | 所有事实、素材、版本、队列任务和来源查询检查项目范围；模型给出的 ID 不代替鉴权 |
| 不可信资料 | 文档中的指令只是待分析内容，不允许改变工具权限或加载上传的 AGENTS.md／Skills |
| 工具最小权限 | 事实、设计、审查工具分开；禁止默认暴露任意数据库写入和通用系统命令 |
| 页面安全 | 限制可执行操作、外部资源与数据绑定；文本和配置验证不替代浏览器侧安全限制 |
| 解析与浏览器 | 限制文件、网络、时间、内存和执行环境；获取网页时防止访问内网与本机敏感地址 |
| 代码扩展 | 在受限候选工作区执行，不挂载个人文件或生产凭据 |
| 凭据与日志 | 不提交密钥、企业资料、数据库备份和完整会话日志；对外展示内容脱敏 |
| 外部模型 | 按授权发送最小所需数据，记录服务使用范围，不声称本地后端等于数据不外传 |

缓存也需带项目与版本范围。不能因为两家企业有同名文档或相同组件，就复用另一家企业的私有事实。

明确原始资料与检查记录的保留政策；无权访问或已删除的来源必须报告真实状态，不伪造可用链接。

## 18. 测试、模型评测与 CI/CD

### 18.1 三类验证不能互相替代

**协议与程序测试**检查格式、权限、版本、计算、依赖和异常处理。**真实 Agent 评测**检查模型是否能完成信息与设计任务。**浏览器检查**验证最终布局、素材、交互和来源入口。

模拟模型输出只能验证工作流处理能力，不能证明 Agent 有真实设计能力。截图只能提供视觉观察，不能代替筛选、展开、来源跳转等功能测试。

### 18.5 CI/CD 的范围

CI 面向代码、协议、Skills、提示词和组件版本；运行时审查面向每次企业生成任务。两者不能混用。

`ci.yml` 逐步接入类型、协议、测试和构建；`agent-evals.yml` 对相关修改或交付版本执行真实模型评测；`deploy.yml` 在实现和检查完成后用于工程部署。首版可以人工触发软件版本部署，不增加企业页面的人工内容审批。

每次变更报告实际运行命令、通过／失败／跳过、已知限制。模型调用费用、延迟和波动单独测量，不写未经实测的加速百分比或并发承诺。

| M3：修订与事实更新 | Router 范围识别、ChangeSet、依赖传播、版本对比、回滚、取消与失败恢复 | A02—A05、A07—A09 等案例的真实测试记录 |
| M4：能力扩展与交付 | 更多格式与表达、系统评测、稳定部署；按需要启用组件工程 | 扩展范围和限制明确，CI 可重复验证，未达标项如实列出 |

按可验证的完整任务路径逐步开发，不在单个任务中要求编程助手“自动完成全部 208 个文件”。文件数量、页面截图和健康检查均不能替代业务能力验收。

### 19.2 第一阶段必须先决定但不在本文伪定的事项

具体 Pi 与运行环境版本、HTTP 框架、队列实现、JSON Schema 验证器、数据库访问层、图表库、首批文件格式及样本。它们应通过短说明与测试确定，不能以“目前还没选库”为理由改变角色和成果协议。

现有骨架倾向 React／TypeScript 前端、TypeScript 后端、Python 解析、PostgreSQL 与对象存储。LangGraph、完整 A2UI 和自动组件工程不是第一阶段必装依赖。

### 19.3 每次开发交付需要报告

实际修改的文件、实现了哪些功能、运行了哪些测试、真实模型调用是否成功、哪些结果是模拟、存在的限制、未完成事项和下一阶段建议。

无凭据、无网络、无依赖或无测试数据时明确报告；禁止隐藏失败、删除检查、把全部审查返回值改成 `pass`、用固定 JSON 冒充 Agent 推理。

### 19.4 同步文档而不覆盖用户文件

实施后更新 `README.md` 的真实启动方式、相关 `docs/` 和测试说明；新增目录后更新 `docs/development/repository-layout.md`。架构改变要登记，并同步本文与专题说明。任何修改都先查看当前文件和 Git 差异，不覆盖用户在解压后已写入的内容。

### 20.2 三个重点项目的简要定位

**ViviDoc：** 面向交互网页文档生成。本文参考其四角色论文版的 Planner、Styler、Executor、Evaluator，以及 DocSpec 连接内容和交互设计的方式。原方法由 Executor 生成网页代码，不是直接使用我们的组件渲染协议。它主要启发“先明确设计，再实现”。[R1](#r01)

**DeepPresenter：** 面向演示文稿的双智能体协作。Researcher 准备结构化稿件与素材，Presenter 负责设计与实现，两者通过观察工具获得实际成果反馈。主要启发专业分工与观察—修正；不能把训练中的外部 Critic 画成本系统直接继承的常驻第三个角色。[R2](#r02)

**screenshot-to-code：** 本项目选择性参考其网页预览工具，尤其是生成桌面和移动端截图并反馈给模型的实现。这里借鉴具体网页工程能力，不把它作为企业信息系统底座，也不将其生成者自检当作我们的独立事实审查。[R3](#r03)

### 21.3 开发完成的判定

“文件存在”“接口返回 JSON”“网页好看”“另一个模型说通过”都不能单独作为完成标准。

**本项目的完成必须能展示：真实业务 Pi 会话执行、企业信息与关系正确、内容驱动的设计、可用交互、可点击原始依据，以及基于当前版本且不越界的后续修改。** 未覆盖的格式、设计能力、异常与指标必须清楚列出。
