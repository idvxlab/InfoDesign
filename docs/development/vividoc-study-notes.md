# ViviDoc v1 阅读与 InfoDesign 对照笔记

日期：2026-10-10。范围：用户提供的 arXiv:2603.27991v1，13 页；已阅读全文并视觉核对第 4、5、7 页的架构、SRTC 和实验表。对照当前快照源码与设计文档，不推断同学未留下记录的学习过程，也未核查 ViviDoc 外部仓库实现。

## 1. 论文究竟解决什么

ViviDoc 面向交互式解释文档：用户给一个主题，系统生成带文字、可视化与交互的 HTML 文档，并允许用户修改规划、风格和结果。它不是以企业多模态资料的事实提取、权限或证据版本管理为核心的系统。

论文第 3 节与第 4 页 Figure 2 的流程：

```text
Topic → Planner → DocSpec → Styler → Style Config
                         DocSpec + Style Config → Executor → Document
                                                        ↑       ↓
                                                        └ Evaluator
```

- Planner：把主题分成有顺序的知识单元，提交符合 Schema 的 DocSpec。
- Styler：根据内容生成写作和交互风格选项，用户可选预设、Auto 或自定义。选择转成自然语言指令提供给 Executor。
- Executor：逐知识单元先生成文字 HTML，再按交互规格生成 HTML/CSS/JavaScript；文字生成参考此前章节以保持一致。
- Evaluator：论文明确描述 HTML 结构、知识单元是否生成完成、章节 HTML 校验；问题反馈可触发局部重新执行。文中没有提供完整企业事实核验算法。

三个用户控制点：生成前编辑 DocSpec、选择 Style Palette、生成后通过聊天修改。论文第 7.1 节定量实验关闭人工干预，风格设为 Auto，因此“支持人工控制”不等于每步必须人工审批。

## 2. DocSpec 和 SRTC

第 4 节：DocSpec 包含主题和有序知识单元，每个单元包含摘要、文字内容说明、SRTC 交互规格。

| 项 | 说明 | 论文圆周率例子 |
| --- | --- | --- |
| State | 变量、类型、范围、默认值、派生规则 | 半径 r 可调；周长 C=2πr、直径 D=2r、比值 C/D 派生 |
| Render | 状态如何显示 | 圆及周长、直径、比值标签 |
| Transition | 用户操作如何改变状态 | 拖动滑块改变半径，相关值同步更新 |
| Constraint | 要展示的不变量或核心认知 | 无论半径如何变化，C/D≈π |

最重要的设计方法是把隐含意图写成可实现、可检查的明确约定。论文没有证明每一个生成的约束都正确，也没有把自然语言 Constraint 自动变成完备的数学验证器。

## 3. InfoDesign 明确借鉴了什么

直接依据是 docs/design/project-spec.md 第 6.1、20.1、20.2 节：记录了 DocSpec 连接设计意图、实现与检查，强调“先明确设计，再实现”；同时明确没有复制 DocSpec，InformationPlan/PageSpec 由本项目定义。

| ViviDoc 方法 | InfoDesign 对应设计 | 当前实现状态 |
| --- | --- | --- |
| 有职责边界的阶段式 Agent | 信息与证据、信息设计、独立审查，由程序编排 | 提取有实际业务实现，审查有运行层，设计/完整编排待实现 |
| 结构化 DocSpec 连接阶段 | EvidenceSnapshot、InformationPlan、PageSpec、ReviewReport | 事实/审查协议已实现；InformationPlan、PageSpec Schema 仍以 not:{} 拒绝所有输入 |
| 规划内容及表达 | InformationPlan 决定选什么、如何组织；PageSpec 描述呈现和交互 | 设计方案已有，业务实现待补 |
| Styler 与风格选项 | 设计角色结合视觉 Skill、DESIGN.md 和品牌约束 | 方法相近；没有论文式 Style Palette 的可用实现 |
| Executor 生成网页代码 | 主路径拟由 PageSpec 驱动已注册组件 | 采用不同实现路线；渲染器和组件仍占位 |
| Evaluator 反馈再执行 | 事实审查与页面审查、定向修正 | 双阶段审查是项目自身安排，B4/B5 尚未完成 |
| 用户编辑规格/聊天修改 | 版本化 ChangeSet、目标节点、范围保护 | 规划，未实现完整交互 |

当前未看到 SRTC 作为权威业务协议落地；不要把 PageSpec 当成 SRTC 的同名替代，也不要声称完整复现了 ViviDoc。

论文没有教团队如何用 Pi SDK 创建这些角色。Pi 是本项目选择的运行时；session-factory.ts、受控工具、权限、候选指纹和独立会话是项目的工程实现。

## 4. 已有提取实现如何体现这种方法

阅读顺序：

1. apps/server/src/agents/evidence/context.ts：固定任务输入、生成程序控制的输出信封、提供资料目录与 Schema。
2. apps/server/src/runtime/pi/skill-loader.ts：从固定路径读取角色提示词和两个提取/归并 Skill。
3. apps/server/src/runtime/pi/session-factory.ts：建立独立 Pi 会话，明确模型与唯一自定义工具。
4. apps/server/src/agents/evidence/agent.ts：调用模型与工具、取严格 JSON、校验、保存、最多一次结构修正。
5. apps/server/src/domain/result-validator.ts：检查来源与实际读取、覆盖、版本及修正保留。

可以观察到“明确角色 → 定义结构化产物 → 程序验收 → 有限反馈”的工程模式。但不能仅凭这种共性断言每一段代码直接源于 ViviDoc；提取、来源和权限功能并非论文对应模块的移植。

## 5. 对事实审查开发最有用的学习点

### 对照成果和明确标准

不要只让模型回答“看起来对不对”。服务应提供固定候选版本、任务范围、必要检查项和可直接读取的原始资料；模型返回有位置、有依据的检查结果。

学习示例（不是现有完整协议实例）：原文为“2025 年末在册研发人员 60 人”，候选写 600。审查者独立读取对应版本原文，核对主体、年份、人数、单位、统计口径，报告数值错误、expected=60、actual=600 和有效证据引用，给出 revise。不能直接修改快照后宣布通过。

### 分开三层检查

- 程序结构层：字段、枚举、引用、项目、版本、内容指纹是否正确。
- 模型语义层：原文是否支持候选，主体、数值、单位、年份、关系是否正确，是否遗漏。
- 工作流层：报告是否可用于当前候选；返回修正、等待资料还是采纳。B4 只提交报告，B5 负责闭环。

已有 checkReviewInput、checkReviewOutput、evaluateAdoption 可以复用，但 B4 仍要验证实际工具读取与报告对应。不要把 JSON 合法或模型写 pass 当成已经读过、核对过。

### 把反馈写到可执行的粒度

报告应定位候选事实与证据，说明哪项错、为什么错、建议返回哪一阶段。新候选再接受新审查，旧报告不能用于新指纹。需要新来源或无法判断时给 needs_input；工具失败属于执行失败，不冒充资料不足。

## 6. 论文评测可学什么、不能证明什么

第 5.2 节把系统评测分成确定性检查和 LLM 打分：IF 用 Playwright 操作控件并观察 DOM 变化；Eff 是输出 HTML 字符数/生成时间；CR 检查内容广度和深度；IQ=ID×IF，把交互设计评分与运行比例结合。

这套离线评测框架与第 3 节运行时 Evaluator 不能混为一谈。也不能据此说其 Evaluator 已完成全部事实或视觉语义核验。

对本项目最值得借鉴的是“先验证行为，再评价质量”。但 DOM 变化不能证明业务结果正确，也可能无法充分衡量 canvas 内部绘制；字符数/秒不能直接衡量企业页面完成速度。上述是对评测方法的局限分析。

第 7.2 节 Table 2：Gemini 3 Flash 下，去掉 DocSpec 的 Naive Agent 与 ViviDoc 的 IQ 分别为 3.24、4.58，IF 为 0.85、0.92，吞吐为 539、505 字符/秒。论文结果支持其测试条件下结构化规划改善质量，同时有规划开销；不是本项目性能承诺，也不证明企业事实准确率。

本项目 B4 应单独测：正确候选通过率、改错检出与误报、遗漏与冲突识别、证据定位、未运行检查的诚实标记、成本和耗时。测试数据要覆盖正确候选及错数值、错主体、错年份、缺证据等情况。

## 7. 建议阅读路线

- 第一遍：论文第 3 节和 Figure 2，理解四角色的输入输出。
- 第二遍：第 4 节及 Table 1，自己写一个 SRTC 例子，练习把含糊意图转成可检查条件。
- 第三遍：第 5.2 节与第 7.2 节，区分“运行正常”“质量更好”和实验支持范围。
- 再回仓库：对照 evidence 的 context/agent/result-validator，最后读 review 的输入输出 Schema 和 backend-plan.md 的 B4。

事实审查可以先用现有合成段落资料独立开发，不必先实现整个 ViviDoc 页面流程。SRTC 更直接服务未来交互设计/页面审查；当前 B4 首先要做好候选与原文的事实对应。

本轮仅做论文阅读与源码对照，未运行项目测试、未执行业务模型、未修改架构或业务代码。
