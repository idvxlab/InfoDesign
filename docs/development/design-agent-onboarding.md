# 页面设计 Agent 接手计划

> 实施更新：2026-10-11 协议与校验、独立 Pi 设计会话、只读工具和一次修正已实现。69 项协议测试、16 项 SDK 模拟网关测试通过；完整回归加审查运行时共 275 项通过。真实模型生成质量、组件渲染与页面审查尚未验收。学习入口和调用方式见[运行时记录](../reports/design-agent-runtime-v1-2026-10-11.md)。下文保留最初接手计划，历史占位状态及待定字段以现行 Schema、源码和本更新为准。

## 最新方向：事实 JSON 到设计协议，再由渲染器生成页面

- 输入主体为已审核并由服务授权使用的事实快照，不让用户重新手工编写企业事实或先指定所有栏目。PDF 是原始证据与素材来源；参考 HTML 只提供设计参考，不能成为该企业事实来源。
- 以实体、事实、关系、事件和素材构建企业内容全景，随后按展示目标选择叙述主线、模块、层级与交互。内容充分不等于堆满全部字段；重要信息应直接可见，细节可展开，并记录省略理由。
- 设计自由体现在布局、配色、排版、信息组合和适当的交互；产品身份、参数、条件、联系方式及证据不得自由补写。派生统计须有输入集合、计算规则和正确标题，不把资料列举量当企业总量。
- InformationPlan 和 PageSpec 是设计 Agent 的正式结构化输出，分别记录内容组织和可执行的页面表达；字段仍待确定。它们由 Agent 生成，不要求用户手工填写。HTML 由声明式渲染器生成。
- 系统最终交付包括可浏览页面、所需资源及元素到快照记录/证据的映射；设计 Agent 本身交付协议候选，技术映射供程序检查，不强迫读者阅读 JSON。
- EvidenceSnapshot 的 assets 目前含 ID、来源位置与描述，没有可直接加载的资源 URL。服务需另提供受控素材映射和可用状态；不能让模型猜文件路径或用装饰图冒充实物图。relations/events 的审核可用范围也由服务明确，不能假定它们具有与 claim 完全相同的逐条审核字段。
- 上游审核只能保证输入范围内的事实基础。页面生成仍可能错配主体、丢失工况、夸大措辞，需对最终页面进行程序检查与独立语义审查。
- 当前先确定两份产物的最小字段、引用和绑定规则，并与组件接口共同验证。真实客户审核 JSON 用于之后的端到端验证，不阻塞当前协议讨论。现有附件只有 Schema 定义；人工试验输入必须标明人工转换及未经过真实上游链路。

本轮核对边界：已读取用户提供 PDF 全部 14 页原生文本，并视觉核对代表性产品/服务页面；HTML 完成结构、样式和脚本静态分析，浏览器 file URL 被安全策略阻止，未验证实际渲染/交互。客户原始资料、摘录和素材未复制到代码仓库。未运行项目测试或业务 Agent。

2026-10-10，静态核对当前仓库后的建议。用户最新分工：同学继续负责审查 Agent，用户转向试做页面设计 Agent。本文是实施建议，不代表已授权或完成下列开发；保持既有三角色和声明式页面架构。

## 目标与边界

设计 Agent 回答“面向谁、展示哪些信息、怎样组织、如何表达和交互”。输入为服务端允许使用的事实快照、企业全景索引、用户目标、受众、约束、视觉规则和实际可用组件目录。输出 InformationPlan 和 PageSpec，必要时报告缺资料或缺组件。

InformationPlan 记录选择/省略及理由、分组、层级、浏览顺序、事实引用；PageSpec 记录稳定节点、组件及版本、布局、样式、交互和事实/证据绑定。它们是同一个设计角色的两层产物，不新增 Planner/Styler 核心角色。

设计 Agent 不修改权威事实、不自行解除冲突、不发布可用页面版本。需要新事实时提出补查；最终页面由同学负责的独立审查能力接入后验收。B4 目前仅规划事实审查，不能假定它自动支持页面审查。

## 核对结果

- agents/design/agent.ts、context.ts、prompt.md 和 tools/design.tools.ts 为占位。
- information-planning、visual-design、page-spec-authoring 三个 Skill 为占位。
- design-input、design-output、information-plan、page-spec 以及组件目录 Schema 尚未实现，继续拒绝输入。
- session-factory.ts 的 SessionRole 只有 probe/evidence/review，且接口只接受单个 ToolDefinition；增加 design 和多工具支持需要共享运行层的小范围变更和回归。
- execution-limits.ts 没有设计角色预算；skill-loader.ts 没有设计资源加载器。
- React 前端、渲染器、组件及其构建入口尚未实现。现有 Timeline 等名称不等于真实可用组件。
- 可复用事实协议、Schema 注册/校验/类型生成、内容指纹、模型配置、执行预算机制、事件记录与传输层。

## 协作接口先确定

与公共后端/审查负责人对齐以下交付约定，开发时固化到 Schema 和测试，不另建平行事实格式：

1. 哪个服务提供可用快照及其确切版本/指纹；如何证明该输入可用于设计。不要让设计模型提交 accepted 或把 B3 pending 候选直接当已通过。
2. 事实全景索引、按 ID 查询事实、读取原始证据的接口。提供主体、关系、时间、单位、口径、缺失与冲突；只给上游摘要不足以支撑设计。
3. 设计输出格式以及节点到事实、关系、事件、素材和原文的引用约定。
4. 组件目录和渲染器的负责人。用户负责 Agent 并不自动意味着还承担全部前端；如果暂无人负责，显式把最小渲染切片列为配套工作。
5. 后续页面审查接收同一版本的快照、计划、规格、渲染结果、浏览器检查结果；事实报告不能充当页面审查报告。

开发可使用人工编制并核对的合成快照，由测试装配提供可信授权上下文，明确标为测试资料；不能冒充真实审查 Agent 通过或写入生产采纳状态。无需等 B4/B5 全部完成才能推进设计模块。

## 建议的四个小阶段

### D1：数据契约与静态样例（第一项交付）

D1—D4 是本文建议的设计侧阶段名，不替代原 B0—B6 后端计划。

- 首轮只支持首次生成；局部修改和 ChangeSet 保持未支持。
- 定义 DesignInput/DesignOutput、InformationPlan/PageSpec 的最小完整字段、引用和版本规则，以及组件定义协议。
- 准备两组结构不同的合成资料，以及同一份事实的两种受众/目标。
- 手写计划与规格作为协议示例，包含合法和非法样例；手写结果明确为测试，不作为 Agent 能力证据。
- 程序检查事实存在、版本匹配、节点唯一、计划/规格对应、组件参数合法、动作受控、来源绑定保留。模型不得写任意 JS 或覆盖关键事实数值。
- 区分已实现组件与规划组件；若没有可用组件，成功生成可渲染 PageSpec 的前置条件尚不成立，应报告能力缺口。common 目前没有 needs_component 状态，草案建议 blocked 加组件需求记录，具体字段待定义。

完成证据：有断言的协议与服务规则测试通过，类型从 Schema 生成且一致；其他占位协议继续拒绝输入。D1 不宣称页面或 Agent 可运行。

### D2：真实设计 Agent 生成规格

- 在现有 Pi 适配层补 design 角色、固定资源加载、独立预算；按需支持工具列表，保留旧角色兼容及权限边界。
- 角色提示词管整体步骤；information-planning 管内容选择，visual-design 管表达，page-spec-authoring 管合法规格生成。
- 提供最小受控只读能力：查询事实、读取证据、查询组件。名称与参数待实现时确定，不声称已有这些 API。
- 先读全景索引，按需补查事实/证据；形成计划，再生成规格并自检。可在同一独立会话分阶段执行，轮数受预算控制。
- 结果经程序验证保存为设计候选；有限反馈修正，失败/取消/截断不得转成完成。
- 未有预览工具时如实记录未预览，不伪造视觉检查。当前模型运行层仅 text 输入，未来看截图还需独立实现视觉输入与预算。

完成证据：真实 Pi 模型/工具执行记录、通过校验的计划/规格或明确能力缺口；两种资料能形成与内容有关的设计决策。模拟网关测试与真实模型结果分别报告。

### D3：实际可交互的预览切片

可与 D2 按共同协议交错推进，避免 Agent 只能选择不存在的组件。

- 先实现一个代表性表达，如 Timeline 或 ComparisonMatrix，并配套必要布局、文本和证据查看能力；登记实际组件能力和版本。
- 再实现另一种不同表达，用不同资料验证结构会随内容变化。不要用一个固定企业首页充当内容驱动设计验收。
- 渲染器读取指定快照，绑定关键数值/事件；来源操作通过受控映射定位原文。预览可先用本地合成数据适配器，不声称正式证据 API 已完成。
- 桌面/窄屏布局、展开/筛选、来源点击实际测试；保存版本匹配的渲染与检查结果。
- 审查尚未接入时明确显示“未独立审查的预览”，不登记最终可用页面。

完成证据：实际页面可操作、内容和事实保持一致、来源能定位，且不是仅打印 JSON。截图不能替代功能检查。

### D4：审查联调与定向修正

独立审查读取原始依据、设计规格与实际页面。事实问题返回证据阶段，表达/布局问题返回设计阶段；程序控制预算和有限修正。通过同一版本完整检查后由服务采纳，不引入每次人工审批。

后续再做基础版本、目标节点与 ChangeSet 支持的自然语言局部修改；首轮不把整个产品范围压进 D1/D2。

## 最小验收矩阵

| 场景 | 预期 |
| --- | --- |
| 事件资料与同口径产品比较资料 | 分别形成有依据的时间/比较表达，不能机械使用同一结构 |
| 同一事实，公众介绍与采购选型目标 | 重点、分组和浏览路径有合理区别，事实不变 |
| 请求突出技术优势但无行业领先证据 | 可以突出已有能力，不能新增领先结论 |
| 资料缺项或关键冲突 | 明确缺口，不能补写未经支持的事实 |
| 必需表达缺少可用组件 | needs_component，说明所需能力 |
| 错误事实 ID、过期快照、未知组件或任意脚本 | 程序拒绝 |
| 模型失败、取消、输出截断 | 有限停止，不保留假成功 |
| 实际点击来源与切换视图 | 保持正确数据、版本和原文位置 |

结构合法、内容忠实、设计合理、页面可操作分别验证。带正确事实引用的文字仍可能夸大含义，不能只靠 ID 校验取代同学的语义审查。
