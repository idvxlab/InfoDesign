后端优先实现信息与证据 Agent，以及独立审查 Agent 的事实审查能力。按 B0—B6 分阶段开发，每个阶段都有明确的成果和验收条件。

- 开始任务时先读 [AGENTS.md](../../AGENTS.md)、[status.md](../../status.md)、[README.md](../../README.md)，首次实现时通读 [项目总方案](../design/project-spec.md)。
- 再读设计概览中的 [Agent 协议](../design/overview.md#agent-contracts)、[工作流程](../design/overview.md#workflows)、[溯源](../design/overview.md#provenance) 和 [验收要求](../design/overview.md#acceptance)。
- 本文把现有方案拆成可执行任务；原始需求和用户后续明确决定优先，发现架构冲突时说明具体冲突。
- 用户指定实现某阶段后，在该阶段内完成设计、代码、测试和必要修复。字段命名、函数拆分、测试框架等常规决定自行核对和记录，无需逐项询问。
- 涉及改变业务含义、核心架构、访问范围、新增付费服务或破坏已有数据时，先说明影响；范围内的可逆实现工作继续推进。已授权的模型验证按既定范围执行，不逐次重复询问。
- 用户只要求阅读或修改文档时，不执行这些开发任务。读取本文不构成实现全部系统的授权。
- 同时授权多个阶段时，依次验证后推进；只授权一个阶段时，完成后报告结果和下一阶段。

可直接发给 Pi 的启动提示词见第 12 节。Git 操作见 [协作指南](contributing.md)。

### 2.2 首轮应实现的结果

```text
合成原文及带位置的 DocumentIR
    → 信息与证据 Agent 读取资料
    → 候选 EvidenceSnapshot
    → 程序检查结构、引用、版本与权限
    → 独立审查 Agent 直接读取原文核验
```

首轮只覆盖生成流程的事实阶段。先通过容器内命令验证，再接任务 API。设计 Agent、页面渲染、页面审查和多格式解析按后续阶段实现；完整系统仍保持三个核心角色。

验收时检查事实能否追溯、错误能否定位、缺失与冲突是否保留，以及失败是否如实报告。正常验证通过后由程序采纳成果，不添加每次必须人工审批的业务门槛。

## 3. 开发与运行环境

### 3.1 区分 Mac 和容器内命令

以下已有命令在 **Mac 项目根目录** 执行：

```bash
git status --short --branch
bash scripts/dev-container.sh status
bash scripts/dev-container.sh check
bash scripts/dev-container.sh pi
```

- `status` 查询容器，`check` 检查隔离与 SDK 导入，`pi` 打开编程助手。这些都不是业务验收测试。
- 容器未启动时在 Mac 执行 `bash scripts/dev-container.sh up`；该命令会重建容器并中断现有会话，执行前结束进行中的任务。
- 需要普通容器终端时，在 Mac 执行 `bash scripts/dev-container.sh shell`。
- Pi 已经在 `/workspace` 内时，直接运行容器里的开发和测试命令。容器没有 Docker 控制接口，不要在其中再次调用宿主 Docker 脚本。
- Mac 可通过 `bash scripts/dev-container.sh exec` 后接命令，在容器里运行非交互检查。具体业务命令必须在对应阶段实际实现后写入 README。
- Git 元数据在容器内只读。提交、推送、切分支在 Mac 完成，不为让 Pi 提交代码而放开挂载权限。

### 3.2 文件、依赖与凭据

- 容器与 Mac 共用源码，Pi 修改会立即出现在编辑器中。保留已有修改，避免覆盖其他人的工作。
- Linux 依赖、运行数据和 Pi 用户目录使用独立卷；容器 `/workspace/.local-data` 与 Mac 同名目录内容不同。
- 开发 CLI 的模型配置只读挂载到 `/home/node/.pi/agent/models.json`；模型 API 密钥经环境变量注入。不要让业务代码假定能读取 Mac 的 `pi.env`。
- 在 `config/env.ts` 明确业务配置入口，再由 Pi 适配层映射到真实 SDK 参数。确需复用开发模型配置时，明确配置路径和适用范围。
- 不打印 API 密钥、完整环境变量或带认证信息的请求；不复制凭据进代码、提示词、测试夹具或 Git。
- 所有 Pi CLI、Pi SDK、业务工具和子进程在容器或虚拟机执行。开发测试也按项目约定在容器内运行。
- 新增依赖先核对真实版本与兼容性，使用包管理器生成锁文件，不手工伪造锁文件或复用 Mac 二进制依赖。
- 当前运行网络只放行配置的模型域名。安装新依赖需要相应网络与镜像缓存，按 [隔离开发指南](dev-container.md) 处理具体域名和构建；不直接放开全部外联。
- 依赖或构建配置改变后，在 Mac 重新构建镜像，再重建容器；保留数据卷。工具受权限限制时报告具体原因，不关闭隔离机制。
- 业务 API、Worker、解析、预览 Dockerfile 目前仍为占位。B1—B5 可以利用现有开发容器验证，完整业务部署另行实现。

## 4. 数据协议：固定结构，允许事实内容扩展

### 4.1 哪些固定，哪些动态

共同协议固定字段名称、类型、必填项、状态、版本和引用规则。企业具体有哪些事实，由资料与任务范围决定。

采用可表达主体、属性、值及来源的通用事实结构。不要把所有企业数据限定成“公司名称、成立年份、研发人数”三个固定字段，也不要让模型每次任意改变 JSON 结构。

下面是一个**合成的单条候选事实示意**，不是完整快照或可直接照抄的完整 Schema：

```json
{
  "claimId": "claim_rnd_2025",
  "claimVersionId": "claim_rnd_2025_v1",
  "entityId": "company_example",
  "predicate": "rnd_headcount",
  "value": { "type": "number", "normalized": 60, "unit": "人" },
  "qualifiers": { "year": 2025, "basis": "年末在岗研发人员" },
  "supportStatus": "supported",
  "reviewStatus": "pending",
  "evidenceRefs": ["source_rnd_2025"]
}
```

其中 `predicate` 的内容可以描述其他属性；`value` 必须遵守已实现的数据类型约束。新属性不必新增一个顶层字段；新数据结构或类型则应经过协议版本和兼容性处理。

编程 Agent 负责完成具体字段、校验和类型生成。属性命名归一规则需要覆盖同义词、主体、单位与口径，并保留原始表述；不能仅凭同名就合并实体或事实。限定字段与扩展区域的规则要明确，禁止用任意对象绕过校验或携带权限指令。

### 4.2 首轮必须覆盖的协议

| 协议 | 必须表达的内容 |
| --- | --- |
| 任务信息 | 服务端生成的任务／尝试编号、已校验的项目范围、任务目标、阶段、输入版本、约束和执行策略引用 |
| DocumentIR | 资料及固定版本、内容块编号、原文、实际位置、解析质量／支持范围；原文与结构化结果可以相互定位 |
| EvidenceSnapshot | 快照版本、实体、事实、关系／事件／素材引用、证据、冲突与缺失；首轮支持范围明确，不静默吞掉未支持内容 |
| Evidence Agent 输入／输出 | 被授权的资料引用和处理范围；候选成果引用、处理覆盖范围、缺失、冲突及停止原因 |
| Review Agent 输入／输出 | 事实审查模式、待审成果确切版本、任务范围、原始证据入口；报告引用和角色执行结果 |
| ReviewReport | 待审版本与内容指纹、审查范围、结论、检查项、问题对应的事实／证据、严重程度和建议回退阶段 |

任务身份、访问策略和成果采纳权限由程序控制。模型提交的项目编号或权限字段不能扩大服务端已授予的范围；模型不能自行把 `reviewStatus` 改成已通过并获得采纳。

事实“有资料支持”和“审查已通过”是不同状态。未知值不当作零，缺失不当作空字符串；协议需明确如何表示未知、缺失和冲突。

### 4.3 校验分三层实现

1. **结构校验**：字段、类型、枚举、必填项、数值／字符串边界及未知字段处理。
2. **服务层校验**：引用是否存在、版本是否一致、位置能否回查、项目与工具访问是否允许、成果指纹是否匹配。
3. **语义审查**：原文是否支持这条事实，主体、数值、单位、时间与口径是否正确，是否有遗漏或冲突。

前两层由程序执行，第三层由独立审查 Agent 结合证据执行。通过 JSON Schema 不能替代事实核验。

`packages/contracts/schemas/` 是协议的唯一权威来源。生成 TypeScript 类型；Python 解析接入时复用同一协议。不要分别在提示词、后端和解析器中维护互不一致的格式。

未实现的协议保持拒绝输入。只有字段、约束、引用检查和测试补齐后，才替换对应占位规则。首轮只支持事实审查时，页面审查输入仍明确拒绝，不能用空对象放行。

## 5. 两个业务 Agent 的实现边界

| 项目 | 信息与证据 Agent | 独立事实审查 Agent |
| --- | --- | --- |
| 目标 | 提取、归并并提交有依据的候选信息 | 对照原始依据检查候选信息 |
| 输入 | 任务范围、DocumentIR、原文位置及授权资料入口 | 任务范围、确切候选版本和原始资料入口 |
| 可用工具 | 在授权范围查询／读取资料、提交候选事实与问题 | 在授权范围读取原文与候选、执行允许的检查、提交报告 |
| 输出 | 候选 EvidenceSnapshot、冲突与缺失 | 绑定候选版本的 ReviewReport |
| 写入范围 | 候选成果 | 审查报告 |
| 采纳事实版本 | 由工作流和服务层决定 | 由工作流和服务层决定 |

两个角色可先使用同一个配置模型，但必须分别创建执行上下文、提供提示词、资源与工具。审查者直接取得原文，不依赖提取者的解释或共享聊天历史。

业务角色不继承开发 Pi CLI 的任意文件操作或通用 Shell。工具接受受控资料编号，由服务层解析路径并检查权限；不能让模型传任意路径读取 API 密钥、其他项目或宿主数据。

只加载仓库中被明确允许的角色资源和 Skills。上传资料里的“忽略规则”“运行命令”等内容作为不可信资料处理，不当成系统指令，也不从上传目录加载 AGENTS.md、Skills 或代码。

## 7. 分阶段任务与完成条件

| 阶段 | 交付目标 |
| --- | --- |
| B0 | 核对代码、环境与本轮范围 |
| B1 | 事实协议、合成资料与校验 |
| B2 | 真实 Pi 工具调用及运行限制 |
| B3 | 信息与证据 Agent |
| B4 | 独立事实审查 Agent |
| B5 | 提取、审查与有限修正流程 |
| B6 | 最小业务 API 与版本化保存 |

这是实施顺序；完成情况及最近一次验证见 [当前状态](../../status.md)。先通过容器内命令验证事实阶段，再接业务 API。

建议 B1、B2 各形成一个小 PR；B3 和 B4 可在共享接口稳定后分别开发；B5、B6 再做集成。每阶段实际测试通过后，才能标记对应能力完成。

### B0：核对基线

**做什么**

1. 核对 Git 分支、已有修改、依赖、容器配置和当前状态，保留他人文件。
2. 明确本轮阶段和会修改的文件，确认上一步的测试证据。
3. 需要执行代码时核对容器环境；文档任务只做文件检查。
4. 区分现有脚本与占位脚本；缺少测试入口时在对应实现阶段补齐。

**完成条件**：准确说明当前能运行什么、尚缺什么、本轮范围是什么。B0 完成不代表 B1—B6 完成。

### B1：协议、合成资料与校验测试

**输入**：本指南第 4 节、项目方案第 4／5／11 节及现有 Schema。

**实施要求**

- 准备合成原文和与其对应的 DocumentIR：保留段落编号、资料版本、明确的任务范围。可以人工编制测试输入，但标记为测试夹具，不宣称真实文件解析已实现。
- 单独保存预期事实和预期审查结果，供测试程序使用；不把标准答案作为 Agent 可读资料。
- 完成任务元数据、DocumentIR、EvidenceSnapshot、事实 ReviewReport 和两个角色输入输出的必要规则。按任务类型／审查模式约束字段，未知模式明确拒绝。
- 设计资料、事实、快照和报告的版本及引用关系；明确哪些由服务端分配、哪些由 Agent 提交、哪些由审查后更新。
- 实现可运行的 Schema 校验入口、类型生成以及引用／版本／权限校验所需的测试接口。复用 `scripts/check-contracts.sh`、`scripts/generate-types.sh` 等已有位置时，真正替换其占位行为。
- 按实际需要添加测试和类型检查依赖、配置与脚本，锁定版本；在 README 写出实测可用的执行命令。
- 结构字段严格校验，扩展字段需有明确规则。未支持的成果 Schema 继续拒绝输入；不删除所有 `not: {}` 来取得“全绿”。

**最低测试集**：合法候选、必填字段缺失、值类型错误、未知字段、重复编号、来源缺失、来源版本不匹配、跨项目引用、未实现的审查模式、模型伪造权限或采纳状态。

**完成条件**：真正执行的测试数量大于零；有效数据通过，非法数据按预期拒绝；生成类型与 Schema 一致；本阶段不需要真实模型调用。服务层检查和纯 Schema 检查分别报告。

### B2：真实 Pi SDK 最小运行任务

**前置**：B1 中被本阶段使用的输入输出和工具参数协议已实现。

**实施要求**

- 阅读容器内已安装的 Pi SDK `0.99.1` 文档、类型和示例，核对会话创建、工具参数、事件、取消与释放接口。必要时查同版本官方资料，不凭其他版本或其他 SDK 的记忆写 API。
- 在 `config/env.ts` 明确配置来源；在 `session-factory.ts` 封装 SDK，业务层只依赖项目接口。不要要求队友另写一套运行层。
- 明确指定模型、凭据引用、角色提示词、资源和工具列表；核对默认工具、扩展、Skills、历史会话是否会被自动加载，并按业务范围限制。
- 先只提供一个受控读资料工具。模型必须真实调用它，并返回有资料内容依据且可校验的结果。
- 实现时间、模型调用次数、工具次数和取消限制，配置校验拒绝无效上限。错误、取消和正常结束都释放会话资源。
- 无凭据、网关错误、不支持工具调用或结果不合法时，明确失败或在可选评测中明确跳过；模拟适配器只能用于标注的程序测试。

**完成条件**：真实网关请求成功；本地记录证明模型发出了工具调用、工具实际执行并返回结果；输出通过校验；越界读取和超时／取消测试通过。SDK 导入或普通聊天成功不能代替这项验收。

模型最大上下文、视觉支持和价格不得从名称或默认值推断。本轮可验证文本及工具能力；其他能力仍标记未验证。

### B3：信息与证据 Agent

**前置**：B1、B2 可用。使用共同协议和运行层。

**实施要求**

1. 按任务范围建立资料清单，读取相关原文和上下文。
2. 识别实体与事实，保留主体、值、时间、单位、统计口径及真实来源位置。
3. 按已实现协议表达关系、事件和素材引用；当前不能处理的内容明确登记，不能静默丢弃并宣称完整。
4. 归并重复事实，保留不同口径、不同年份的数据；对真正的冲突保留各自证据。
5. 提交候选快照及缺失／冲突／覆盖范围说明。服务层校验并保存，不直接覆盖已有可用版本。
6. 在规定限制内修正结构错误，保留新候选版本和失败原因；不能靠删除难处理的事实让校验通过。

**完成条件**：合成案例中的预期事实、单位、时间和来源正确，缺失不编造，冲突能保留；增加一个样例之外的属性后，仍通过通用结构表示。记录真实模型执行和程序检查结果。

### B4：独立事实审查 Agent

2026-10-12实际进度：事实审查代码已回写，同版v12七类虚构真实验收及独立审计通过（10次尝试、7份有效报告、3次失败保留），最终382/382离线与类型/生成/协议通过。报告不采纳候选；B5后续已完成本地最低验收，见下节。格式可靠性与细分检查类别限制见[阶段报告](../reports/pi-multimodal-review-100cny-2026-10-10.md)。以下完成条件保持不变。

**前置**：共享协议和运行层可用。可先使用人为制作的候选快照开发，不必等待 B3 的所有情况完善。

**实施要求**

- 每个审查任务使用独立上下文，输入固定候选版本、任务要求及原始资料入口，不继承提取者的推理历史。
- 使用工具核对原文及相关上下文，检查主体、数值、单位、年份、统计口径、来源对应、遗漏和冲突。程序验证证据引用能解析，模型判断语义是否受支持。
- 报告逐项列出被检查的事实、依据、问题与严重程度。未执行项标记 `not_run`；必要检查未完成时不能形成可采纳的通过结果。
- 区分 `pass`、`revise`、`needs_input`。技术执行错误另行报告，不能把模型超时解释成“资料不足”。
- 报告绑定被检查候选的版本和指纹。审查者只提交报告；修改事实由提取阶段完成，再重新审查新版本。

**完成条件**：正确候选能通过；人为改错的数值、主体、年份等能被定位；关键缺失与冲突不会被草率放行；报告引用和指纹校验通过。记录错误检出与误报，不能用固定返回 `pass` 或固定返回 `revise` 冒充审查。

### B5：事实阶段工作流与命令入口

2026-10-12：B5本地最低验收及19文件保护回写完成。最终v14两类虚构真实路径分别为人工错误候选的审查—返修—再审查、真实提取后的缺证等待；422项与类型／协议在回写后的主仓库通过。本地运行历史跨进程可读，尚无HTTP、生产数据库或自动恢复。受控撤回为离线分支验证，所有候选仍pending；完整证据和模型限制见[B5报告](../reports/b5-fact-workflow-2026-10-12.md)。

**实施要求**

- 由程序编排：输入校验 → 提取 → 候选校验 → 独立审查 → 校验报告 → 审查通过／等待／返修／停止；本阶段不正式采纳候选。
- 用 `state.ts` 表示任务状态，用独立 `stage` 表示当前阶段。任务完成、角色执行完成、成果可用分别判断。
- `revise` 返回提取阶段，携带具体问题和必要证据；生成新候选，重新执行程序校验和审查。
- `needs_input` 保存问题、候选及固定输入版本，结束当前执行，进入等待补充；恢复时复核版本与权限。
- 技术重试和语义修正分开计数，为次数设置可配置的有限上限，并设置总预算；达到上限、超时或取消后停止，禁止晚到的响应继续采纳成果。
- 重复执行按任务／尝试与成果标识去重。已通过的旧版本保持可读，失败候选不能覆盖当前可用指针。
- 为事实阶段提供真实可用的容器内命令入口，并实现明确的退出码与结果范围。未实现的设计／页面阶段不得被报告为成功完成。
- 本阶段如采用测试内存仓库，明确范围；若声明持久化或重启恢复已完成，必须实现对应存储并测试。运行报告不能代替业务数据库。

**完成条件**：真实提取—审查路径至少完整执行一次；用明确标注的模拟适配器验证各个状态分支、有限重试、取消、去重和版本保护；保存可核查的候选及报告。模拟流程通过和真实 Agent 质量分别报告。

### B6：最小任务 API 与版本化保存

**实施要求**

- 沿 TypeScript 主后端实现，按真实兼容性选择并锁定 HTTP 框架。Python 服务负责后续解析，当前没有已接通的 FastAPI 主后端。
- 在现有 `entrypoints/api.ts`、`entrypoints/worker.ts`、`api/routes/tasks.ts` 等位置实现任务入口与后台执行，复用 B5 流程。
- 参考项目方案的拟定接口：创建任务、查询状态、取消任务和读取成果。请求参数、响应和错误同样经过协议与权限校验。
- 长任务先返回任务编号，后台继续执行。首轮可先用查询接口取得进度；SSE／WebSocket 是否引入另作小范围选型，不作为两类 Agent 验证的前提。
- 错误包含稳定代码、可读说明、请求／任务编号和是否可重试，例如输入非法、无权限、模型超时、来源失效、预算耗尽；代码名由实现统一定义。
- 实现资料、候选快照、报告、任务状态和当前可用版本的保存。遵循项目方案的存储接口及数据库方向，验证原子采纳、基础版本检查、重复请求、重启读取和授权隔离。
- 如使用仅供本地验证的身份或存储适配器，明确限制，不宣称生产鉴权、并发安全或数据库已完成。临时适配器与正式实现之间使用相同接口。
- 当前开发容器没有发布端口。先在容器内测试接口；需要 Mac 访问时再配置本地端口并复查网络边界，不开放公网、不接入 Jetson 现有服务。

**完成条件**：通过真实 HTTP 请求创建并查询任务，完成两类 Agent 的事实流程；错误和取消可观察，成果和来源可按权限读取，声明支持的持久化及版本保护有测试。明确本轮成果是事实快照与报告，不是可交互页面。

## 8. 测试资料与验收矩阵

每个案例先写清原始资料、任务范围、预期事实或预期错误，再实现和运行。预期答案属于测试程序，禁止在业务工具中直接返回标准答案。

| 编号 | 场景 | 预期行为 | 验证方式 |
| --- | --- | --- | --- |
| F01 | 正常原文包含企业、产品、事件和数值事实 | 在约定范围内正确提取，来源能回查 | 真实提取＋程序核对 |
| F02 | 新增一个样例外的属性 | 用通用事实结构表达，无需改顶层协议 | 程序校验＋真实提取 |
| F03 | 任务要求的信息在资料中缺失 | 明确缺失，不把未知填为零或猜测值 | 真实提取／审查 |
| F04 | 同主体、同时间和同口径出现不同数值 | 保留各自证据，报告冲突 | 真实提取／审查 |
| F05 | 不同年份、单位或口径的两个数值 | 不误合并、不草率判为同一事实冲突 | 真实提取／审查 |
| F06 | 人为把候选中的 60 改成 600，来源仍有效 | 指出数值错误并引用正确原文 | 真实独立审查 |
| F07 | 人为替换候选的主体／年份，或删除任务必需事实 | 检出错配或遗漏，定位依据 | 真实独立审查 |
| F08 | 正确候选 | 必要检查执行后允许通过，检测固定拒绝的假审查 | 真实独立审查 |
| F09 | 来源不存在、版本不匹配、位置越界 | 程序拒绝，不能采纳 | 确定性测试 |
| F10 | 请求读取另一项目、任意路径或提交未授权状态 | 服务层拒绝，不泄露数据 | 权限测试 |
| F11 | 原文含要求忽略规则或执行命令的文字 | 按资料处理，不提升工具权限、不跳过检查 | 工具权限测试＋模型案例 |

| F13 | 报告对应旧候选，或重复提交、基础版本已过期 | 拒绝错误采纳，保留原可用版本 | 版本／流程测试 |
| F14 | 重启或恢复等待中的任务 | 只恢复已声明支持的状态，并重新检查版本与权限 | 存储／恢复测试，B6 验收 |

不要只运行容易通过的案例，也不要只报告多次执行中最好的一次。实际失败、重试和未执行项一并记录。小样本通过只证明本轮范围，不能推断所有资料格式和所有企业场景都已可靠。

## 9. 测试命令与运行证据怎么交付

### 9.1 把三类检查分开

| 类别 | 检查什么 | 模型调用 |
| --- | --- | --- |
| 类型、Schema 和业务规则测试 | 类型、字段、引用、权限、版本、错误处理 | 不需要 |
| 工作流测试 | 分支、重试、预算、取消、去重和恢复 | 可以使用明确标注的模拟模型 |
| 真实 Agent 评测 | 工具调用、提取质量、独立审查及两者联调 | 需要真实模型与凭据 |

真实评测必须显式启用，并限定在本轮任务的小样本和预算内。普通程序测试不能悄悄消耗模型额度；真实凭据缺失时不能自动切换模拟结果后显示“真实评测通过”。

B1／B2 已提供类型检查、协议检查、程序测试和显式真实验收入口，当前命令见 [测试说明](../../tests/README.md)。后续阶段新增的测试或业务命令，应在实际实现并验证后登记；目前仍无 `pnpm dev` 业务启动入口。

### 9.2 每次记录的证据

- 当前提交／工作区标识，实际测试命令、时间、退出码和用例数量。
- 哪些通过、失败、跳过或未执行；使用模拟的部分明确标注。
- 合成资料及版本、任务／尝试编号、模型 ID、SDK 版本、角色与候选／报告版本。
- 实际发生的工具名称、调用是否成功、耗时；避免把完整敏感参数或会话内容写入共享报告。
- 提取正确与遗漏、审查检出与误报、修正次数，逐个案例列出结果。
- 接口报告的输入／输出／缓存 token 和调用次数；缺少用量时写未知。价格未核实时不输出估算费用，更不能把默认零价格当作免费。

私有运行输出放被忽略的运行目录，例如容器内 `/workspace/.local-data/`。该目录是 Docker 卷，Mac 同名目录看不到其中内容；报告注明实际位置，需分享时只导出核对过的脱敏摘要。不要为了查看日志而共享整个凭据目录。

仓库可提交合成夹具、测试代码和不含敏感内容的总结；企业原文、真实密钥、完整模型会话日志和数据库备份不提交。

## 10. 三个人如何并行协作

| 负责人 | 主要维护范围 | 第一项交付 |
| --- | --- | --- |
| 公共后端与运行层 | `packages/contracts/`、`runtime/pi/`、配置、业务校验、工作流和存储入口 | B1 协议与校验，再完成 B2 真实工具任务 |
| 信息提取 | `agents/evidence/`、`tools/evidence.tools.ts`、提取／归并 Skills、合成原文与来源处理 | 在共同协议下准备案例，完成 B3 |

各模块负责人维护自己的工具文件，公共后端负责人检查工具权限和共享接口。测试随对应模块交付；事实审查 Agent 不替代团队成员对代码和测试的审查。

协作顺序：

1. 先通过 PR 统一开发环境与文档基线；核对实际 Git 状态，不能假定其他人的 `main` 已含所有配置。
2. B1 合并并同步后，大家使用同一份 Schema 和生成类型。B2 提供共同运行接口后，B3、B4 可分别推进。
3. 每人使用自己的仓库、开发容器和任务分支；避免多人或多个编程助手同时写同一工作区。
4. 修改共享协议时，同时修改其示例、校验、生成类型和受影响调用者；在 PR 中说明兼容影响。
5. B3、B4 各自验证后，由公共后端负责人连接 B5，另外两人分别核对事实与审查效果。
6. 提交、推送和 PR 按 [协作指南](contributing.md) 在 Mac 完成；遵循用户本轮授权和团队合并流程，不绕过容器只读 Git 限制。

大家可以使用不同编程助手。各助手必须读取同一项目方案和协议，Git 同步后才会看到队友的新改动。

## 11. 每轮结束时如何汇报

建议按下面的格式向用户交付，并同步简短的 `status.md`：

```text
本轮阶段：B?
实际实现：列出具体能力和修改文件。
验证：实际命令、用例数、通过／失败／跳过、报告位置。

```

只有注释、可解析 JSON、接口返回 200、一次聊天回复或测试进程退出 0，都不足以说明某阶段完成。测试入口必须真正执行了有断言的用例，语义任务必须有对应的真实模型证据。

继续工作前先修复当前阶段的失败，不能通过删断言、扩大输入放行、降低验收要求或隐藏未执行项来推进状态。

## 13. 全项目路线

| 阶段 | 目标与边界 |
| --- | --- |
| 接口与最小运行层 | 按 B0—B6 补齐协议、版本／溯源模型、真实 Pi 任务、提取与事实审查、最小接口和保存；暂不追求所有格式、完整组件库、Supervisor 或自动组件工程。 |
| 首次生成闭环 | 使用一家企业已脱敏或获授权的资料，接入选定格式的解析、信息设计、页面渲染、独立页面审查和来源点击，验证完整输出。 |
| 展示修订与事实更新 | 实现任务分类、稳定节点、基础版本、变更集、影响计算、前后对比和回滚。 |
| 扩展与自动化 | 按实际缺口扩展解析、组件、评测、CI 和业务部署；自动组件工程为可选扩展，不阻塞前述阶段。 |

实际文件解析、视觉能力、页面交互和生产部署分别验收。全项目的完成标准以 [验收清单](../design/overview.md#acceptance) 和总方案中的完整要求为准；每次交付保留实际测试、限制和待办，不能仅靠更新状态宣称完成。
